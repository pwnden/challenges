## 시나리오 설정

- 표시 제목: 회원 계정으로 운영 화면 열기
- 한 줄 소개: 고객지원 관리자 핀보드가 알림 번호가 문의 목록에 없다는 제보를 받고, 일반 회원 계정이 운영 화면까지 열 수 있는지 시험 사이트에서 확인해 달라고 의뢰한다.
- 공개 닉네임과 말투: 핀보드. 해요체로 짧게 설명한다. “알림을 받았어요”, “확인하지 못했습니다”처럼 확인한 일과 확인하지 못한 일을 구분해 말한다.
- 의뢰인과 플레이어의 역할: 의뢰인은 전시 모임 고객지원 관리자다. 플레이어는 시험 사이트에서 일반 회원 `member`로 시작해 문의 조회·초대 등록·운영 화면 열기를 사용한다.
- 대상과 사건의 계기: 고객지원 사이트의 문의, 운영 초대, 운영 화면이다. 일반 회원이 자기 문의 목록에 없는 번호의 알림을 받았다는 제보가 계기다. 제보는 시나리오 설정이며 실제 고객 사고의 주장이 아니다.
- 길드를 찾은 이유: 이 문제는 직접 해결이 막힌 이유와 소개·이전 의뢰 같은 길드와의 접점을 따로 정하지 않았다. 브리핑은 핀보드가 같은 상황의 시험 사이트를 준비해 확인을 맡기는 데까지만 쓴다.
- 이번에 공개할 정보: 계정 `member`, 문의 목록과 번호 조회, 운영 초대 등록, 운영 화면의 존재와 제출 대상. 알림 번호의 쓰임과 초대 코드의 출처, 두 기능의 연결은 공개하지 않는다.
- 의뢰 목표와 완료 증거: 일반 회원 계정으로 운영 화면을 열 수 있는지 확인한다. 운영 화면의 접속 확인 코드 `pwnden{...}` 전체를 제출한다.
- 처음 전달할 사실: 문의 본문은 작성자만 읽을 수 있어야 하고, 운영 담당자는 자기 계정에 발급된 초대 코드를 등록해 합류하며, 운영 담당자만 접속 확인 코드를 볼 수 있어야 한다. 이는 운영 원칙이며 현재 구현이 지킨다는 뜻이 아니다.
- 사건의 흐름: 회원이 목록에 없는 번호의 알림을 받는다 → 핀보드가 문의와 초대 기능이 계정 권한에 영향을 주는지 확인하려 한다 → 시험 사이트와 일반 회원 계정을 준비한다 → 플레이어가 두 기능을 조사한다. 구현은 `vulnerable/app.py`의 `Desk`와 문의 `310`·`311`에서 이 흐름과 일치한다.
- 조사 중 발견할 사실: 문의 `310` 본문이 알림 번호 `311`을 언급한다. 번호 조회는 작성자를 확인하지 않아 `311`의 본문과 초대 코드를 읽을 수 있다. 초대 등록은 코드와 사용 여부만 확인하고 수신 계정을 확인하지 않는다.
- 풀이자에게 남긴 판단: 목록에 보이는 범위와 번호로 읽을 수 있는 범위를 비교할지, 알림 번호를 어디에 쓸지, 읽은 코드를 어느 기능에 쓸지를 풀이자가 정한다. 본문과 화면 안내는 이 판단을 알려 주지 않는다.
- 학습 목표와의 연결: 문의 본문의 노출이 초대 등록의 권한 변경으로 이어지는 경로를 직접 만들어 보면 한 기능의 허점이 다른 기능의 권한 문제로 확대되는 이유를 관찰할 수 있다.

## 학습 목표와 대상

- 현재 계약의 category: web
- 학습 분야: web-security. 한 기능에서 새어 나온 자료가 다른 기능의 권한 변경으로 이어지는 경로를 입증하는 것이 목표다.
- 세부 주제: web-access-control. 개별 자료의 소유권 확인 다음 단계인 여러 접근 경로의 연결을 다루므로 이 주제의 진행 문제로 둔다.
- category 선택 근거: 브라우저 화면과 HTTP 서비스로 풀므로 현재 계약의 web이다.
- 보안 학습 목표: 일반 회원 계정으로 다른 계정의 문의를 읽고 그 초대 코드로 운영 권한을 얻는 경로를 입증하고, 두 기능이 각각 현재 계정을 확인해야 하는 이유를 설명한다.
- 확인할 보안 원리: 각 기능은 자기 작업의 권한을 서버가 현재 계정으로 확인해야 한다. 앞 기능의 비밀 유지에 기대면 다른 경로로 코드가 노출되었을 때 뒤 기능이 잘못된 권한을 부여한다.
- 대상 풀이자: 웹 주소와 요청·응답을 이해하고 개별 자료의 소유권 확인을 경험한 보안 입문자. 제공된 화면의 폼과 버튼만 사용하며 CLI, 개발자 도구, Python 능력은 요구하지 않는다.
- 시작 조건과 성공 증거: 일반 회원 `member`로 시작한다. 운영 화면의 접속 확인 코드가 서버의 응답으로 표시되면 성공이다.

## 선수 지식과 학습 내용

| 필요한 능력 | 역할: 선수 지식 / 학습 목표 / 배경 | 필요한 풀이 단계 | 제공 위치: 개념 자료 / 본문 / 힌트 / 해설 |
| --- | --- | --- | --- |
| 웹 주소에서 경로와 번호 구분 | 선수 지식 | 번호 입력으로 다른 문의를 조회 | 개념 자료 `web-addresses` |
| 요청과 응답의 상태·본문 읽기 | 선수 지식 | 403과 200, 응답 본문의 코드 구분 | 개념 자료 `http-messages` |
| 목록 범위와 개별 자료 접근 범위의 구분 | 선수 지식 | `311` 조회 결과와 목록 비교 | 개념 자료 `object-ownership`, 힌트 1 |
| 초대 코드와 수신 계정의 구분 | 학습 목표 | 코드를 등록하고 계정은 그대로 권한만 바뀌는 것을 관찰 | 개념 자료 `invitation-boundaries`, 힌트 2, 해설 |
| 서버가 저장한 역할로 보호된 화면 열기 | 배경 | 등록 뒤 운영 화면에서 접속 확인 코드를 읽음 | 본문, 힌트 3, 해설 |

## 의도된 풀이

| 단계 | 풀이자가 수행할 행동 | 발견·관찰할 내용 | 필요한 지식·도구 |
| --- | --- | --- | --- |
| 1 | 시작 화면에서 계정과 권한을 확인하고 `운영 화면 열기`를 누른다. | 계정은 `member`, 권한은 일반 회원이고 운영 화면은 거부된다. | 웹 화면 |
| 2 | 문의 `310`을 열어 본문의 알림 번호를 읽는다. | 목록에 없는 번호 `311`이 나온다. | 웹 화면 |
| 3 | 문의 번호에 `311`을 입력해 조회한다. | 작성자 `staff-new`의 문의 본문과 초대 코드가 현재 계정에도 보인다. | `object-ownership` |
| 4 | 표시된 초대 코드를 운영 초대 폼에 등록한다. | 등록이 성공하고 계정은 `member`로 남지만 권한은 운영 담당자로 바뀐다. | `invitation-boundaries` |
| 5 | `운영 화면 열기`를 누르고 접속 확인 코드를 제출한다. | 서버가 운영 화면에서 `pwnden{...}`를 반환한다. | 웹 화면 |

보안 학습 목표와의 연결: 3단계가 문의 조회의 소유권 문제를, 4단계가 초대 등록의 계정 확인 문제를 보여 주고, 5단계가 두 문제의 연결이 실제 권한 상승이라는 결과임을 확인한다.

풀이자의 언어 지식: 화면의 폼과 버튼만으로 풀 수 있다. 코드 이해나 작성은 필요하지 않다.

## 개념 관계

- 문제의 선수 개념: `web-addresses`, `http-messages`, `object-ownership`.
- 문제의 학습 개념: `invitation-boundaries`.
- 개념 간 선수 관계: `invitation-boundaries`는 `object-ownership`을 요구한다. `object-ownership`은 `trusted-identity`를 요구하므로 순환이 없다. 검증 도구가 카탈로그의 순환을 검사한다.
- 관련 읽기: `read-path-authorization`. 여러 읽기 기능의 권한 일관성을 다룬다.
- 공개 위치: 선수 개념은 시작 전 읽을 수 있고 학습 개념은 풀이 후 확인하는 학습 목표 문서다. 개념 문서는 편집자 `editor-a`와 독자 `reader-b` 예제를 쓰며 이 문제의 계정·번호·코드를 쓰지 않는다.

## 난도 근거

- 선언한 값: 3 (1 입문, 2 초급, 3 중급, 4 고급, 5 심화)
- 선수 지식 부담: 웹 주소, 요청·응답, 자료의 소유권. 소유권은 `note-vault` 수준의 경험을 전제한다.
- 발견 난도: 목록에 없는 번호를 직접 조회해 보는 일, 읽은 코드를 초대 폼에 쓰는 일, 두 기능의 연결을 풀이자가 스스로 이어야 한다. 알림 번호의 쓰임과 코드의 출처는 알려 주지 않고, 힌트가 순서대로 범위를 좁힌다.
- 구현 부담: 코드·계산·도구 사용이 없다. 화면 조작만 필요하다.
- 풀이 의존성: 3단계에서 얻은 코드가 4단계에서 필요하고 4단계의 권한이 5단계의 조건이다. 한 단계라도 건너뛰면 성공하지 못한다.
- 등급 판정: 난도 2인 `refund-loop`는 한 기능 안의 금액 비교이고 이 문제는 두 기능을 이어야 해서 한 단계 높게 둔다. 작성자 판단이며 학습자 관찰로 확정하지 않았다.

manifest의 difficulty를 바꾸면 이 기록도 함께 갱신하세요.

## 다른 풀이와 정답 노출

- 확인한 다른 풀이: 운영 화면 직접 열기는 `solve.py`가 거부(403)를 확인했다. 코드 추측은 18바이트 난수라 현실적이지 않다고 판단했지만 실행으로 확인하지 않았다. 별도 세션의 코드를 쓰는 방법은 세션마다 코드가 달라 쓸 수 없다. `solve.py`가 별도 세션의 운영 화면 거부를 확인한다.
- 의도치 않은 지름길 점검: 화면과 API 어디에도 접속 확인 코드를 미리 담지 않는다. 운영 화면은 서버에 저장된 역할을 확인하며, `tests/scenarios.test.ts`가 서버 렌더링 상태에 `pwnden{`이 없음을 확인한다.
- 본문 노출 점검: 본문은 문의 번호나 코드의 쓰임을 알려 주지 않는다. 화면 안내는 번호 조회가 가능하다는 기능 설명까지만 쓴다. `311`이라는 번호는 문제 안에서 문의 `310` 본문에 있고 구체적인 순서는 힌트 3과 해설에만 있다.
- 필요한 힌트: 3개. 1번은 목록 범위와 조회 범위의 차이, 2번은 작성자와 초대받은 계정의 확인, 3번은 `311` 조회와 코드 등록 순서를 다룬다.
- 해설: 다섯 단계의 재현, 두 결함이 각각 필요한 이유, 수정 서버의 두 비교를 설명한다. 정상 수신자의 등록 허용과 “두 검사는 각각 필요하다”는 코드에서 읽은 설계 설명이며, 한 검사만 되돌린 대조 서버는 실행하지 않았다.

## 검증과 리뷰

- 실행 범위: 실제 대상. 서비스 하나를 Docker로 실행하고 플레이어 도구는 웹이다. 수정 서버는 `compose.patched.yaml`로 `policy.py`만 바꿔 실행한다.
- 기술 검증: 2026-10-13, 카탈로그 형식 검사 22개, 작성자 실행기 `verify.py ticket-bridge`(풀이·수정 서버 대조·정리), Vue 타입 검사와 렌더링 테스트 14개를 통과했다. 같은 날 브라우저에서 풀이 흐름 전체와 모바일 폭의 줄바꿈을 확인했다. 수정 대조는 수신 계정으로 접속하는 경로가 없어 정상 수신자의 등록을 직접 확인하지 않는다.
- 학습 리뷰: 독립 리뷰어의 풀이 관찰은 아직 없다. `quality/reviews/ticket-bridge.json`의 일곱 항목이 모두 미평가이다.
- 리뷰 관찰: 문장 검토에서 브리핑의 “잘못된 알림”이 확인할 대상을 단정한 표현이라 “받은 알림”으로 고쳤다. 기록은 `quality/text-reviews/ticket-bridge/2026-10-13-review.md`에 있다.
- 맥락 확인: 문장 검토가 첫 의뢰 메시지만으로 의뢰인과 대상의 관계, 증상, 확인할 일을 식별하는지 확인했다. 실제 처음 읽는 사람의 정리는 아직 받지 않았다.
- 용어 확인: 브리핑, 화면, 힌트, 해설이 알림·문의·초대 코드·운영 화면을 같은 이름으로 부르는지 대조했다. 화면과 해설은 접속 확인 코드를 같은 용어로 쓴다.
- 배포 준비 상태: 기술 검증은 충족했다. 독립 학습 리뷰가 남아 있어 배포 준비 완료로 표시하지 않는다.
