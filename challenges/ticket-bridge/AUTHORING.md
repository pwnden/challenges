# 회원 계정으로 운영 화면 열기

## 대상과 학습 설계

- 학습 분야: web-security. 주제: web-access-control.
- 대상: 주소와 웹 폼을 사용할 수 있고 개별 자료의 소유권 확인을 경험한 보안 입문자.
  난도 3은 두 기능의 결함을 따로 찾는 데서 끝나지 않고, 한 기능에서 얻은 자료를
  다른 기능에 연결해야 하는 풀이 부담을 뜻한다.
- 선수 능력: 웹 주소, 요청·응답, 자료의 소유권과 읽기 권한. 제공된 화면만으로
  문의 조회·초대 등록·운영 화면 열기와 제출을 수행한다. CLI, 개발자 도구,
  Python 능력은 요구하지 않는다.
- 학습 목표: 한 기능에서 새어 나온 자료가 다른 기능의 권한 변경으로 이어지는 경로를
  입증하고, 두 기능이 각각 현재 계정을 확인해야 하는 이유를 설명한다.
- 의뢰인 핀보드는 전시 모임 고객지원 관리자다. 알림 번호가 문의 목록에 없다는 제보를
  받고 일반 회원 계정이 운영 화면까지 열 수 있는지 확인해 달라고 맡긴다.
  제보는 시나리오 설정이며 실제 고객 사고의 주장이 아니다.
- 참고한 패턴: 작은 정보 노출이 다음 기능의 권한 문제와 이어지는 연쇄 구조.
  OWASP Juice Shop과 이용자 토론에서 여러 기능을 연결하는 경험을 원한다는 반응을
  참고했다. 이 대상은 문의 본문 조회와 초대 등록 두 기능만 사용한다.

## 판단과 제공 정보

기본 브리핑은 계정의 시작 권한·조사 대상 기능·접근 방법·제출 대상을 제공한다.
화면은 문의 목록, 번호 조회, 초대 등록, 운영 화면을 보여 준다. 풀이자는 목록에
보이는 범위와 번호로 읽을 수 있는 범위가 같은지 먼저 판단해야 한다. 알림 번호와
초대 코드를 어디에 쓰는지는 기본 본문과 화면 안내에 알려 주지 않는다.
힌트는 목록 밖의 알림 → 초대받은 계정 확인 → 두 기능을 이은 구체적인 순서로 제공한다.
학습 목표 문서는 문제와 독립된 편집자·독자 예제로 초대 코드와 수신 계정의 차이를 설명한다.

## 구현과 대조

`vulnerable/app.py`는 쿠키별 Desk를 유지한다. 계정은 `member`, 역할은 `member`로
시작하고 초대 코드는 Desk마다 새로 생성한다. 문의 `311`의 작성자는 `staff-new`이며
본문에 초대 코드가 있다. 문의 조회는 `ticket_allowed`, 초대 등록은
`invitation_allowed`가 판단한다. 취약한 정책은 두 함수 모두 항상 허용한다.
수정한 정책은 문의 작성자와 현재 계정, 초대의 수신 계정과 현재 계정을 비교한다.
초대는 코드가 맞고 아직 쓰지 않았을 때만 등록하며 등록한 코드는 다시 쓸 수 없다.
운영 화면은 서버에 저장된 역할만 확인하고 그때 생성된 FLAG를 반환한다.
프런트에는 정답이나 자체 권한 판정을 넣지 않는다.

풀이 검증은 시작 상태의 거부, 본인 문의 `310` 조회, 타 계정 문의 `311`의 코드 노출,
코드 등록 뒤 계정은 그대로이고 역할만 바뀌는 것, 운영 화면의 플래그, 별도 세션의
분리를 확인한다. 수정 서버에서는 같은 풀이가 `311` 조회에서 거부되어 종료 코드 3을
반환한다. 수정 대조는 본인 문의 조회, 없는 번호·잘못된 번호·잘못된 코드의 거부,
운영 화면 거부, 초기화와 세션 격리를 확인한다.
수정 대조는 정상 수신자가 초대를 등록하는 경로를 직접 확인하지 않는다.
이 대상에는 수신 계정으로 바꿔 로그인하는 기능이 없고 두 검사를 따로 분리해
실행하는 검사도 없다. 초대 등록 검사를 단독으로 확인하는 대조는 아직 없다.
