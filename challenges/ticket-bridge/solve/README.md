## 조사 결과

회원 계정은 자기 목록에 없는 문의 본문을 읽고, 거기에 적힌 다른 계정의
운영 초대를 사용할 수 있었다. 운영 화면은 서버에 저장된 역할을 확인했지만,
초대 등록 기능이 잘못 바꾼 역할을 그대로 받아들였다.

## 조사 과정

1. 전시 모임 고객지원을 열면 계정은 `member`, 권한은 일반 회원이다.
   먼저 `운영 화면 열기`를 누르면 서버가 접근을 거부한다.
2. 내 문의 `310`을 연다. 본문에 내 목록에 없는 알림 번호 `311`이 나온다.
3. 문의 번호에 `311`을 입력해 조회한다. 작성자는 `staff-new`인데,
   현재 회원 계정에서도 본문과 운영 초대 코드를 읽을 수 있다.
   내 목록에서 숨기는 것만으로 본문 읽기를 막지는 못했다.
4. 표시된 초대 코드를 복사해 운영 초대 폼에 등록한다. 서버는 코드와 미사용
   여부를 확인하지만 초대받은 계정과 현재 계정이 같은지 확인하지 않는다.
   현재 계정은 여전히 `member`이고 권한만 운영 담당자로 바뀐다.
5. `운영 화면 열기`를 누르면 접속 확인 코드가 나온다.

초대 코드는 시험 계정마다 다르다. 초기화했다면 문의를 다시 조회해야 한다.
코드를 추측하거나 다른 시험 계정의 코드를 가져올 필요는 없다.

## 의뢰 완료 확인

운영 화면의 `pwnden{...}` 전체를 제출한다. 초대 등록 성공 메시지만으로는
완료가 아니다. 서버가 운영 화면에서 접속 확인 코드까지 반환하는 것을 확인한다.

## 드러난 보안 원리

첫 결함은 문의 번호로 본문을 읽을 때 작성자를 확인하지 않는 것이다.
두 번째 결함은 초대 코드가 유효하다는 이유만으로 다른 계정의 권한을 바꾸는 것이다.
두 결함이 이어지면 정보 노출이 계정 권한 변경으로 확대된다.

수정 서버는 문의의 작성자와 현재 계정을 비교하고, 초대의 수신 계정과 현재
계정도 비교한다. 초대 코드를 알고 있어도 대상 계정이 다르면 등록을 거부해야 한다.
정상 수신자의 등록은 허용하고, 사용한 코드는 다시 사용할 수 없게 유지한다.
운영 화면의 역할 확인도 그대로 필요하다.

두 검사는 각각 필요하다. 문의 조회만 고치면 다른 경로로 코드를 알게 된 경우의
초대 오용이 남고, 초대 등록만 고치면 다른 사람의 문의 내용 노출이 남는다.
목록·본문·초대·최종 화면마다 해당 작업의 권한을 서버가 확인해야 한다.
