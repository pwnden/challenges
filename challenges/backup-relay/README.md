백업을 읽을 수 있게 만들었는데, 방금 손님 계정으로 접속해서 AUTH 없이 READ만

중계기의 명령 몇 개와 손님용 테스트 토큰을 드릴 테니 실제로 AUTH 단계를

:person[자물쇠지기]는 작은 운영팀의 백업 중계기를 관리한다. 중계기는 팀
내부망에서만 접속되는 TCP 서비스이며, 과거에 폐기된 백업과 현재 사용 중인
백업을 `READ` 명령으로 조회할 수 있다. 자물쇠지기는 현재 백업을 아무나 읽지
못하도록 `AUTH` 단계를 먼저 통과해야만 `READ`가 응답하게 만들었다고 설명한다.

손님 계정으로 접속한 팀원이 안내된 순서(HELLO → AUTH → READ)를 따르지 않고
AUTH를 건너뛴 채 `READ`만 보냈는데도 응답을 받았다는 제보가 들어왔다. 자물쇠지기는
직접 재현해 보지 못했고, `STATUS` 명령은 인증 전후로 다른 값을 돌려주는 것까지는
확인했다. AUTH가 실제로 `READ`의 허용 여부에 쓰이는지는 아직 확인되지 않았다.

플레이어에게는 중계기 주소와 손님용 테스트 토큰이 주어진다. 테스트 토큰은
`AUTH`가 정상 동작하는지 확인하는 용도이며, 그 자체로는 현재 백업을 읽을 권한을
주지 않는다. 조사 대상은 현재 백업의 내용이며, 이미 폐기된 백업의 값은 제출
대상이 아니다.

::objective
AUTH 단계를 거치지 않고도 현재 백업을 읽을 수 있는지 확인하자.
::

::resources

- 대상 호스트: 문제 네트워크 안의 `app`, 포트 9000.
- 프로토콜: 줄바꿈으로 끝나는 텍스트 명령. `HELLO`, `AUTH <token>`, `STATUS`, `READ <name>`.
- 손님용 테스트 토큰: `relay-guest-7f2c` (AUTH 동작 확인용이며 현재 백업 열람 권한은 주지 않는다).
- 폐기된 백업 이름: `backup-retired` (제출 대상 아님).
::

::submission
AUTH 단계 없이 현재 백업에서 읽은 `pwnden{...}` 값을 제출하자. 실행 환경을 새로
준비하면 값이 바뀐다.
::
