## 시나리오 설정

- 표시 제목: 백업 중계기의 연결 상태

- 한 줄 소개: 운영팀의 백업 중계기 관리자가 AUTH 단계를 건너뛴 READ 제보를 조사해 달라고 의뢰한다.
- 공개 닉네임과 말투: 자물쇠지기. 차분하고 실무적인 말투로 자신이 관리하는 서비스의 상태를 정확히 보고한다.
- 의뢰인과 플레이어의 역할: 자물쇠지기는 중계기 관리자, 플레이어는 손님 계정으로 접속해 제보를 재현하는 조사자다.
- 대상과 사건의 계기: 팀 내부망의 백업 중계기. 손님 계정이 AUTH 없이 READ만 보냈는데 응답을 받았다는 제보.
- 길드를 찾은 이유: 자물쇠지기가 직접 재현해 보지 못했고, 손님 계정 권한만으로 외부 검증이 필요했다.
- 이번에 공개할 정보: 중계기의 명령 네 개와 손님용 테스트 토큰. 서버 코드나 `authenticated` 변수 이름은 공개하지 않는다.
- 의뢰 목표와 완료 증거: AUTH 없이 READ backup-current에서 읽은 현재 flag 제출. 새 연결에서 HELLO 뒤 바로 READ만 보내도 성공해야 한다.
- 처음 전달할 사실: 중계기 주소·포트, 네 개 명령, 테스트 토큰, 폐기 백업 이름(제출 대상 아님).
- 사건의 흐름: 평소에는 HELLO → AUTH → READ 순서로 쓰임 → 손님이 순서를 어겼는데 응답을 받음(제보) → 자물쇠지기가 재현 못 함, STATUS만 인증 전후 차이를 확인함 → 조사 권한(호스트·포트·명령·테스트 토큰) 전달 → 현재 백업의 실제 열람 가능 여부 조사.
- 조사 중 발견할 사실: STATUS는 인증 상태를 반영하지만 READ는 반영하지 않는다는 비교.
- 풀이자에게 남긴 판단: 어느 명령을 먼저 보낼지, AUTH 전후 STATUS·READ 응답을 비교해 추론을 세우는 일.
- 학습 목표와의 연결: "안내 문서의 순서"와 "실제 구현이 확인하는 상태"가 다를 수 있음을 직접 관찰한다.

## 학습 목표와 대상

- 현재 계약의 category: "misc"
- 학습 분야: System/Network security(`learning-map.md`) 중 `network-protocol-state` — TCP 서비스가 선언한 순서를 실제로 강제하는지 확인하는 체험.
- 세부 주제: `network-protocol-state`의 진입 사례("A TCP service accepts an operation before its required step")를 그대로 따른다.
- category 선택 근거: 기존 misc 분류(`diagnostic-port`)와 같은 포트·TCP 조사 범주이며, 아직 `web`·`pwn`·`rev`·`crypto`·`forensics`에 맞지 않는 순수 TCP 프로토콜 문제다.
- 보안 학습 목표: 다단계 프로토콜에서 각 명령이 세션 상태를 스스로 확인해야 하며, 문서화된 순서만으로는 그 확인을 보장하지 않는다는 것을 설명할 수 있다.
- 확인할 보안 원리: 인가 상태 확인 누락(연결 상태 추적은 존재하지만 모든 명령이 그 상태를 읽지는 않음).
- 대상 풀이자: 터미널에서 `ncat`으로 줄바꿈 텍스트 프로토콜에 명령을 보내고 응답을 비교할 수 있는 풀이자. `tcp-services` 선수 지식을 가정한다.
- 시작 조건과 성공 증거: 호스트·포트·네 개 명령·테스트 토큰이 주어진다. AUTH 없이 READ backup-current가 현재 flag를 반환하면 성공이다.

| 터미널에서 ncat으로 TCP 텍스트 프로토콜에 줄 단위 명령을 보내고 응답을 읽는다 | 선수 지식 | 전체 | 개념 자료(`tcp-services`) |

## 의도된 풀이

| 단계 | 풀이자가 수행할 행동 | 발견·관찰할 내용 | 필요한 지식·도구 |
| --- | --- | --- | --- |
| 1 | `ncat`으로 `app:9000`에 접속해 `HELLO`를 보낸다 | 배너와 지원 명령 목록 확인 | `tcp-services` |
| 2 | `STATUS`를 AUTH 전후로 비교한다 | `role=guest` → `role=staff`로 바뀜, 인증 상태가 실제로 기억됨 | 힌트 1 |
| 3 | 새 연결에서 AUTH 없이 바로 `READ backup-current`를 보낸다 | `DENIED`가 아니라 `OK pwnden{...}` 응답 | 힌트 2 |
| 4 | `READ backup-retired`와 비교해 폐기 자료는 항상 공개임을 확인하고 현재 flag만 제출한다 | 대조군으로 결론을 뒷받침 | 해설 |

보안 학습 목표와의 연결: 2단계는 "서버가 상태를 기억한다"는 사실을 세우고, 3단계는 "그 상태를 모든 명령이 확인하지는 않는다"는 결함을 직접 관찰하게 한다. 4단계의 대조군은 폐기 자료가 애초에 비보호 자료임을 분리해, 결함이 "READ가 인증을 확인하지 않는다"는 지점에 있음을 좁힌다.

풀이자의 언어 지식: 코드 작성이나 읽기는 필요 없다. 제공된 네 개 명령을 텍스트로 조합해 서버 응답을 비교하는 것만으로 충분하다.

## 개념 관계

- 문제의 선수 개념: `terminal-commands`, `tcp-services`(`knowledge/tcp-services.md`).
- 문제의 학습 개념: `connection-state`(`knowledge/connection-state.md`) — 세션이 기억해야 하는 연결 상태.
- 개념 간 선수 관계: `connection-state`는 `tcp-services`를 선수로 한다. 순환 없음.
- 관련 읽기: `diagnostic-port`(포트별로 다른 기능이 노출되는 별개의 misc 문제, 같은 ncat 조작을 재사용).
- 공개 위치: 네 개 명령과 테스트 토큰은 본문에서 공개. AUTH가 READ에 쓰이지 않는다는 결론은 힌트·해설에서만 명시한다.

## 난도 근거

- 선언한 값: 2 (1 입문, 2 초급, 3 중급, 4 고급, 5 심화)
- 선수 지식 부담: `tcp-services`만 있으면 되고, 새 프로토콜 명령은 본문이 모두 설명한다.
- 발견 난도: STATUS 비교로 상태 추적을 확인한 뒤, READ에도 같은 확인이 있는지 스스로 시험해야 한다. 단서 연결이 필요해 입문보다 높다.
- 구현 부담: 코드 작성 없이 ncat 명령 조합만 필요하다.
- 풀이 의존성: 2단계(STATUS 비교)가 3단계(READ 시험)의 가설을 만든다.
- 등급 판정: diagnostic-port(2, 포트 조사)보다 발견 단계가 한 단계 더 필요해 같은 등급의 상한에 해당한다.

manifest의 difficulty를 바꾸면 이 기록도 함께 갱신하세요.

## 다른 풀이와 정답 노출

- 확인한 다른 풀이: HELLO 생략 후 바로 READ만 보내는 경로도 동일하게 성공함을 `solve.py`로 확인했다(배너 소비 여부와 무관).
- 의도치 않은 지름길 점검: `READ backup-retired`는 고정된 더미 flag 형태 문자열이라 정답 형식만으로 혼동되지 않는지 확인했다. 값이 `retired_backup_cleared`로 고정되어 있어 매 실행 생성되는 현재 flag와 형태로 구분된다.
- 본문 노출 점검: 본문은 명령 네 개의 구문만 제공하고 어떤 조합이 성공하는지는 말하지 않는다. 명령을 그대로 따라 하면 안내된 순서(HELLO → AUTH → READ)가 성립하는 정상 경로만 재현되고, AUTH 생략은 풀이자가 직접 시도해야 한다.
- 필요한 힌트: 1번은 STATUS 비교라는 관찰 방향을, 2번은 AUTH 생략이라는 구체적 시도를 제공한다. 본문만으로는 안내된 순서를 의심할 단서가 부족해 2개를 유지한다.
- 해설: `solve/README.md`에 전체 재현, STATUS·READ 대조, 패치 뒤 동작까지 기록했다.

## 검증과 리뷰

- 실행 범위: 실제 대상. `tools/verify.py backup-relay`로 취약한 서버에서 solve가 flag를 회수하고, 패치 서버에서는 거부됨을 확인했다(날짜는 검증 로그 참고).
- 기술 검증: 2026-10-14, `tools/verify.py backup-relay` 통과. `patched/test.sh`가 HELLO·STATUS·AUTH 성공/실패·READ 성공/거부·미지원 명령·형식 오류를 모두 확인한다.
- 학습 리뷰: 미완료(독립 리뷰어 관찰 필요).
- 리뷰 관찰: 미완료.
- 맥락 확인: 처음 읽는 사람이 자물쇠지기·중계기·AUTH 제보·조사할 일을 첫 메시지만으로 식별할 수 있는지 `quality/text-reviews/backup-relay/`에서 확인한다.
- 용어 확인: 본문·힌트·해설이 모두 같은 명령 이름(HELLO, AUTH, STATUS, READ)과 같은 자원 이름(backup-current, backup-retired)을 쓴다.
- 배포 준비 상태: 기술 검증 통과. 학습 리뷰(독립 관찰)는 아직 비어 있어 배포 전 보완이 필요하다.
