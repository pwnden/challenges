# 시나리오 작성 기록

이 기록은 2026-10-13에 문제 파일과 `quality/` 기록을 읽고 처음 작성했다. 문제를 만들 때 남긴
작성 기록은 없었으므로 설계 의도를 당시 작성자에게 확인한 내용이 아니다.

## 시나리오 설정

- 표시 제목: 다른 사람의 메모
- 한 줄 소개: 개인 메모 사이트 운영자가 목록에서 숨긴 메모가 다른 계정에도 막히는지 길드에 확인을 맡긴다.
- 공개 닉네임과 말투: 정해진 닉네임이 없다. 브리핑은 운영자를 직책으로만 부르고 서술체로 쓴다. README에 의뢰 `message` 블록이 없다.
- 의뢰인과 플레이어의 역할: 운영자가 게스트 계정 `guest`를 전달하고, 플레이어는 이 계정으로 로그인해 메모를 조사한다.
- 대상과 사건의 계기: 관리자 계정 `admin`의 메모에 복구 키가 있다. 평소 목록에서 숨겨진다는 사실만으로 다른 사용자의 접근이 막히는지 확인하려는 것이 계기다.
- 길드를 찾은 이유: 브리핑에는 운영자가 길드에 확인을 맡겼다고만 적혀 있고 직접 해결이 막힌 이유는 없다.
- 이번에 공개할 정보: 계정 `guest`/`guest`, 자기 메모 `Welcome` 하나가 목록에 보인다는 것, 관리자의 복구 키가 있다는 것, 제출 형식.
- 의뢰 목표와 완료 증거: 게스트 계정으로 관리자의 메모를 읽고 복구 키 `pwnden{...}`를 제출한다.
- 처음 전달할 사실: 메모는 작성한 계정의 개인 자료이고 다른 계정에는 공개되면 안 된다는 운영 원칙.
- 사건의 흐름: 운영자가 계정별 목록은 만들었지만 개별 메모를 여는 요청의 확인 여부는 알지 못한다 → 게스트 계정을 주고 점검을 맡긴다.
- 조사 중 발견할 사실: 자기 메모를 열면 주소에 메모 번호가 보인다. 번호를 바꾸면 관리자의 메모가 열린다.
- 풀이자에게 남긴 판단: 주소의 번호를 바꿔 볼지, 어떤 번호를 시도할지를 풀이자가 정한다. 힌트 하나가 주소를 살펴보라고만 안내한다.
- 학습 목표와의 연결: 목록에서 숨기는 것과 개별 자료를 읽을 때 권한을 확인하는 것이 별개임을 직접 관찰한다.

## 학습 목표와 대상

- 현재 계약의 category: web
- 학습 분야: web-security
- 세부 주제: web-access-control. 학습 지도에서 이 주제의 진입 문제로 `note-vault`를 지정한다.
- category 선택 근거: 브라우저와 HTTP 서비스로 풀므로 web이다.
- 보안 학습 목표: 로그인한 계정으로 다른 계정의 메모를 번호만 바꿔 읽는 경로를 입증하고, 요청마다 소유자를 확인해야 하는 이유를 설명한다.
- 확인할 보안 원리: 인증과 인가는 다르다. 목록의 필터가 아니라 자료를 읽는 요청이 소유권을 확인해야 한다.
- 대상 풀이자: 브라우저와 주소를 읽을 수 있는 입문자. 난도 1.
- 시작 조건과 성공 증거: `guest`로 로그인해 시작하고, 관리자 메모 본문의 `pwnden{...}`가 성공 증거다.

풀이자의 언어 지식: 화면과 주소만으로 풀 수 있다. 코드 읽기나 작성은 필요하지 않다.

## 개념 관계

- 문제의 선수 개념: `web-addresses`, `http-cookies`, `trusted-identity`.
- 문제의 학습 개념: `object-ownership`.
- 개념 간 선수 관계: `object-ownership`은 `trusted-identity`를 요구한다. 순환이 없음은 검증 도구가 확인한다.
- 관련 읽기: `path-boundaries`.
- 공개 위치: 선수 개념은 시작 전, 학습 개념은 풀이 후 확인한다.

## 난도 근거

- 선언한 값: 1 (1 입문, 2 초급, 3 중급, 4 고급, 5 심화)
- 선수 지식 부담: 웹 주소와 쿠키, 서버가 확인하는 신원.
- 발견 난도: 번호가 주소에 드러나 있어 한 값만 바꾸면 된다. 기록에 별도 난도 분석은 없다.
- 구현 부담: 코드·계산·도구 사용이 없다.
- 풀이 의존성: 단계가 둘뿐이다.
- 등급 판정: 별도 기록이 없다. 입문 문제로 선언되어 있다.

## 다른 풀이와 정답 노출

- 확인한 다른 풀이: `solve/solve.py`는 JSON API `/api/notes/2`를 쓴다. 화면 주소 `/notes/2`도 같은 정책을 통과한다는 것을 `patched/test.py`가 확인한다.
- 의도치 않은 지름길 점검: 목록과 홈은 로그인한 계정의 메모만 반환하고 정답 본문은 관리자 메모에만 있다. 이를 직접 대조한 기록은 없다.
- 본문 노출 점검: 본문은 번호를 바꾸라는 말을 하지 않는다. 힌트 하나가 주소를 살펴보라고 안내한다.
- 필요한 힌트: 1개.
- 해설: 풀이 단계, 원인, 방어와 인증·인가의 구분을 설명한다.

## 검증과 리뷰

- 실행 범위: 실제 대상. 서비스 하나를 Docker로 실행하고 수정 서버는 `compose.patched.yaml`로 `policy.py`만 바꾼다.

- 학습 리뷰: `quality/reviews/note-vault.json`과 `quality/text-reviews/note-vault/`에 2026-10-04의 기록이 있다. 독립 초보자의 풀이 관찰은 아니다.
- 리뷰 관찰: 문장 검토에서 수정할 문장 불일치가 없었다고 기록되어 있다.
- 맥락 확인: 위 문장 검토 기록을 따른다.
- 용어 확인: 위 문장 검토 기록을 따른다.
- 배포 준비 상태: 이 기록으로 판단하지 않는다. 품질 기록의 평가 항목이 일부 미평가이다.
