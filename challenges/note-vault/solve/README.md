## 핵심: 메모를 열 때도 권한을 확인하는가

이 서비스는 목록에서는 내 메모만 보여 주지만, 메모 하나를 여는 요청에서는 소유자를 확인하지 않는다. 로그인한 사용자가 메모 번호를 바꾸면 다른 사람의 내용을 읽을 수 있다.

### 1. 자신의 메모를 연다

메모 사이트에서 아이디와 비밀번호에 각각 `guest`를 입력한다. 로그인 후 보이는 메모를 열면 주소 끝이 `/notes/1`이다.

### 2. 주소의 번호를 바꾼다

같은 브라우저 탭에서 주소의 `/notes/1`만 `/notes/2`로 바꾸고 접속한다. 다른 주소 부분은 유지한다. 관리자 메모가 열리고, 본문에 `pwnden{...}` 형식의 복구 키가 보인다.

그 값을 복사해 이 작업 화면의 플래그 입력란에 제출한다. 실행마다 새 키가 생기므로 해설에 적힌 고정된 정답은 없다. 현재 실행 중인 메모에서 읽은 값이 정답이다.

### 3. 왜 읽을 수 있었을까

목록을 반환하는 경로는 메모의 소유자가 로그인한 사용자와 같은지 확인한다. 반면 개별 조회는 메모 번호로 내용을 찾은 뒤 그대로 반환한다. 사용자는 목록을 거치지 않고도 개별 주소를 요청할 수 있으므로 목록의 필터만으로는 보호할 수 없다.

같은 세션에서 `/api/notes/2`를 열어도 내용을 읽을 수 있다. 화면과 데이터 응답 모두 조회 시점의 권한 검사가 필요하다. 이런 결함을 **IDOR**라고 부른다. 사용자가 바꿀 수 있는 식별자를 통해 권한 없는 객체에 접근하는 문제다.

### 4. 올바른 방어

메모를 읽는 모든 요청에서 로그인 여부와 해당 메모의 소유자를 함께 확인해야 한다. 자신의 메모는 계속 읽을 수 있어야 하고, 다른 사람의 메모는 거절해야 한다. 번호를 복잡하게 만들거나 목록에서 감추는 것만으로는 권한 검사를 대신할 수 없다.

### 배운 점

**인증**은 누구인지 확인하고, **인가**는 그 사람이 해당 자료를 읽어도 되는지 확인한다. 로그인에 성공했다고 모든 메모를 볼 권한까지 생기지는 않는다. 다른 객체의 주소를 직접 요청해 보는 습관으로 이 차이를 확인할 수 있다.
