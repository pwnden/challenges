## 조사 결과

`req-205`는 게스트가 운영 계정의 자료를 성공적으로 읽은 요청이다.
같은 요청 번호의 응답 내용 기록에서 실제로 전달된 복구 키를 확인했다.

## 조사 과정

1. `access.log`에서 게스트 요청을 모은다.

   | 요청 ID | 주소 | 상태 |
   | --- | --- | --- |
   | `req-202` | `/exports/9` | 200 |
   | `req-203` | `/secure-exports/42` | 403 |
   | `req-204` | `/exports/99` | 404 |
   | `req-205` | `/exports/42` | 200 |

2. 성공한 `req-202`와 `req-205`를 `audit.jsonl`에서 찾는다.
3. `req-202`의 소유자는 `guest`다. 자신의 자료를 정상적으로 내보낸 기록이다.
4. `req-205`의 소유자는 `ops`다. 요청자와 소유자가 다른데도 응답이 성공했고,
   `response.recovery_key`에 복구 키가 기록됐다.
5. 거부된 `req-203`의 응답은 오류다. 유출의 근거는 성공 상태와 실제 응답 내용이다.

## 의뢰 완료 확인

`req-205`에서 읽은 `pwnden{follow_the_request_not_the_clock}`를 제출한다.

## 드러난 보안 원리

요청 기록과 서버가 보낸 내용의 기록을 같은 요청 번호로 연결하면 누가 어떤 자료를 실제로 받았는지 확인할 수 있다.
이 자료의 실험 사이트에는 소유자를 확인하는 경로와 확인이 빠진 이전 내보내기 경로가 함께 있었다.
이전 경로를 통한 접근이 운영 계정의 복구 키를 노출했다.

파일 정렬 순서와 근접한 시각만으로 사건을 연결하면 다른 요청을 섞을 수 있다.
이번 판단의 근거는 같은 요청 ID, 성공 상태, 서로 다른 요청자와 소유자, 실제 응답이다.
이 기록으로 확인할 수 있는 범위는 해당 요청의 자료 전달이며, 이후 키 사용이나 접근자의
실제 신원은 추가 증거가 필요하다.
