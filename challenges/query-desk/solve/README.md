## 조사 결과

검색어가 SQL 조건에 그대로 붙었다. 검색어 안의 작은따옴표와 조건식을 통해
공개 회원만 보여 주던 제한을 바꾸고 비공개 회원의 복구 키를 읽었다.

## 조사 과정

1. `mira`를 검색한다. 실행 조건은 다음과 같고 공개 소개 하나가 나온다.

   ~~~sql
   SELECT name, note FROM members WHERE name = 'mira' AND public = 1
   ~~~

2. `'` 하나를 검색하면 이름을 감싸던 따옴표가 중간에서 닫혀 검색 조건 오류가 나온다.
3. `' OR 1=1 -- `를 검색한다. 다음 조건이 실제 데이터베이스에서 실행된다.

   ~~~sql
   SELECT name, note FROM members WHERE name = '' OR 1=1 -- ' AND public = 1
   ~~~

   `1=1`은 항상 참이다. `-- ` 뒤는 설명으로 처리되는 **주석**이므로
   공개 여부를 확인하던 `AND public = 1`도 실행에서 빠진다.
4. 결과에 `keeper`가 포함된다. 소개 칸에서 현재 복구 키를 읽는다.

`' OR public=0 -- `처럼 비공개 행을 직접 고르는 조건으로도 같은 결과를 확인할 수 있다.

## 의뢰 완료 확인

`keeper`의 소개에 표시된 `pwnden{...}`를 제출한다. 키는 실행할 때마다 바뀌므로 현재 사이트에서 읽는다.

## 드러난 보안 원리

데이터로 받아야 할 입력을 명령의 일부로 조합하면 입력이 실행 구조를 바꿀 수 있다.
이 사이트는 SQLite라는 데이터베이스를 사용한다. 조건 화면에는 실제로 실행한 SQL이 표시된다.

수정한 서버는 `WHERE name = ? AND public = 1`의 `?` 자리에 검색어를 별도 데이터로 전달한다.
검색어의 따옴표와 `OR`도 이름 데이터로 취급되고, 공개 여부 조건은 유지된다.
공개 회원의 정상 검색은 그대로 동작한다.
