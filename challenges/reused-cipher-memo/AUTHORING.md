## 시나리오 설정

- 표시 제목: 재사용된 메모 봉인

- 한 줄 소개: 메모 보관소 운영자가 점검용 CHECK 기능이 메모 봉인과 같은 패드를 재사용하는지 확인해 달라고 의뢰한다.
- 공개 닉네임과 말투: 봉인지기. 차분하고 실무적인 말투로 자신이 운영하는 보관소의 기능과 확신이 서지 않는 부분을 정확히 보고한다.
- 의뢰인과 플레이어의 역할: 봉인지기는 보관소 관리자, 플레이어는 CHECK와 MEMO의 관계를 조사하는 조사자다.
- 대상과 사건의 계기: 메모 하나를 무작위 패드로 봉인해 저장하는 TCP 보관소. 점검용 CHECK 기능이 같은 패드를 재사용하는지 운영자 스스로 확신이 없음.
- 길드를 찾은 이유: 봉인지기는 CHECK를 점검용으로 켜 두기만 했고, 실제로 메모와 같은 패드를 쓰는지 직접 검증해 보지 못했다.
- 이번에 공개할 정보: 대상 호스트, 명령 세 개(HELLO, MEMO, CHECK)와 CHECK의 입력 길이 제한. 패드가 고정인지 매번 새로 만드는지는 공개하지 않는다.
- 의뢰 목표와 완료 증거: CHECK가 메모와 같은 패드를 재사용하는지 확인하고 메모 원문(flag)을 복원한다. 복원한 값이 `pwnden{...}` 형식이면 완료다.
- 처음 전달할 사실: 대상 호스트·포트, 세 명령의 구문, CHECK 입력 길이 제한(1~128바이트).
- 사건의 흐름: 메모는 무작위 패드로 봉인된다고 알려짐 → 점검용 CHECK 기능이 추가됨 → 봉인지기가 CHECK와 메모의 패드가 같은지 확신하지 못함 → 조사 권한(호스트·명령 구문) 전달 → 패드 재사용 여부와 메모 원문 조사.
- 조사 중 발견할 사실: 같은 입력을 CHECK에 반복해도 항상 같은 응답이 온다는 관찰, 그리고 그 응답을 MEMO의 응답과 조합하면 원문이 나온다는 관계.
- 풀이자에게 남긴 판단: CHECK에 어떤 값을 보내 패드 재사용을 확인할지, 얻은 값들을 어떻게 조합해 원문을 복원할지.
- 학습 목표와의 연결: 표현 변환과 보호의 차이(`encoding-secrecy`)를 넘어, "한 번만 써야 하는 값을 다시 쓰면 그 값 자체를 계산해 낼 수 있다"는 관계를 직접 관찰한다.

## 학습 목표와 대상

- 현재 계약의 category: "crypto"
- 학습 분야: Cryptography 중 대칭키 재사용 — 일회용 패드(또는 스트림 키)를 재사용하면 패드 자체를 계산해 낼 수 있다는 체험.
- 세부 주제: 점검·디버그 기능이 운영 자료와 같은 키 자료를 재사용해 키 복구 경로를 여는 사례.
- category 선택 근거: 기존 crypto 분류(`wrapped-secret`, `hash-lantern`, `signed-delivery`)는 모두 입문·초급의 "정적 파일 분석" 문제다. 이 문제는 상호작용 가능한 오라클(CHECK)을 더해 같은 분야의 중급 문제를 채운다.
- 보안 학습 목표: XOR 기반 암호화에서 같은 패드를 재사용하면, 그 패드로 암호화한 값 중 하나를 알거나 직접 고를 수 있을 때 패드 자체와 다른 암호문의 평문을 계산할 수 있음을 설명할 수 있다.
- 확인할 보안 원리: 키(패드) 재사용으로 인한 기밀성 붕괴. 점검용 오라클이 운영 자료와 같은 키 자료를 공유하는 설계 결함.
- 대상 풀이자: 터미널에서 `ncat`으로 텍스트 프로토콜을 다루고, `python3`로 16진수·바이트·XOR 연산을 짧게 작성할 수 있는 풀이자. `terminal-commands`와 `encoding-secrecy` 선수 지식을 가정한다.
- 시작 조건과 성공 증거: 호스트·포트와 세 명령의 구문이 주어진다. `CHECK`로 얻은 패드와 `MEMO`의 응답을 조합해 `pwnden{...}`를 복원하면 성공이다.

## 의도된 풀이

| 단계 | 풀이자가 수행할 행동 | 발견·관찰할 내용 | 필요한 지식·도구 |
| --- | --- | --- | --- |
| 1 | `ncat`으로 `app:9200`에 접속해 `HELLO`, `MEMO`를 보낸다 | 배너, 지원 명령, 메모의 봉인된 16진수 값 확인 | `terminal-commands` |
| 2 | 같은 값을 `CHECK`에 두 번 보내 응답을 비교한다 | 항상 같은 응답, 패드가 고정돼 있다는 가설 | 힌트 1 |
| 3 | `MEMO` 응답과 같은 길이의 0 값을 `CHECK`에 보내 패드를 얻고, `MEMO` 응답과 XOR한다 | `pwnden{...}` 형태의 원문 복원 | 힌트 2 + 해설, `python3` |

보안 학습 목표와의 연결: 2단계는 패드가 요청마다 달라지지 않는다는 사실을 세우고, 3단계는 그 고정된 패드를 실제로 계산해 내 원문을 복원하는 결과로 보안 원리를 직접 확인하게 한다.

풀이자의 언어 지식: 16진수·바이트열·XOR 연산을 짧은 `python3` 코드로 작성할 수 있어야 한다. 그 외의 코드 작성이나 읽기는 필요 없다.

## 개념 관계

- 문제의 선수 개념: `terminal-commands`, `encoding-secrecy`(`knowledge/encoding-secrecy.md`).
- 문제의 학습 개념: `stream-key-reuse`(`knowledge/stream-key-reuse.md`) — 재사용된 키와 두 암호문의 관계.
- 개념 간 선수 관계: `stream-key-reuse`는 `encoding-secrecy`를 선수로 한다. 순환 없음.
- 관련 읽기: `wrapped-secret`(표현 변환과 보호의 차이를 다루는 같은 crypto 분류 입문 문제).
- 공개 위치: 세 명령의 구문과 CHECK의 길이 제한은 본문에서 공개. 패드가 고정이라는 사실과 복원 방법은 힌트·해설에서만 명시한다.

## 난도 근거

- 선언한 값: 3 (1 입문, 2 초급, 3 중급, 4 고급, 5 심화)
- 선수 지식 부담: `encoding-secrecy`로 "표현 변환은 보호가 아니다"는 배경만 있으면 되고, XOR과 패드 개념은 본문·힌트가 설명한다.
- 발견 난도: 정적 파일을 들여다보는 기존 crypto 입문 문제와 달리, 상호작용 가능한 오라클(CHECK)의 응답을 반복 관찰해 재사용 여부를 스스로 가설로 세워야 한다.
- 구현 부담: 16진수·바이트·XOR 변환을 짧은 `python3` 코드로 직접 작성해야 한다.
- 풀이 의존성: 2단계(반복 관찰로 세운 재사용 가설)가 3단계(패드를 실제로 계산해 원문 복원)의 전제가 된다.
- 등급 판정: `wrapped-secret`·`hash-lantern`(1, 정적 파일 분석)보다 오라클 상호작용과 코드 작성이 더해져 중급(3)으로 둔다.

manifest의 difficulty를 바꾸면 이 기록도 함께 갱신하세요.

## 다른 풀이와 정답 노출

- 확인한 다른 풀이: `CHECK`에 0이 아닌 임의의 고정 평문을 보내고 `CHECK(p) XOR p`로 패드를 구해도 동일하게 복원됨을 `solve.py`를 변형해 확인했다(0 값은 계산을 단순화할 뿐 유일한 경로는 아니다).
- 의도치 않은 지름길 점검: `CHECK`의 길이 제한(1~128바이트)이 메모 길이보다 항상 크거나 같은지 확인했다(`FLAG`는 생성 규칙상 128바이트를 넘지 않는다). 길이가 부족해 패드 일부만 복구되는 경우는 없다.
- 본문 노출 점검: 본문은 명령 구문과 길이 제한만 제공하고, 패드가 고정인지 매번 새로 만드는지는 말하지 않는다. 명령을 그대로 한 번씩만 보내면 MEMO의 봉인 값만 얻을 뿐 원문은 복원되지 않는 정상 경로가 먼저 재현된다.
- 필요한 힌트: 1번은 반복 관찰이라는 방향을, 2번은 0 값으로 패드를 얻는 구체적 계산을 제공한다. 본문만으로는 XOR 성질을 이용한 복원 경로를 추측할 단서가 부족해 2개를 유지한다.
- 해설: `solve/README.md`에 전체 재현, 복원 계산의 원리, 패치 뒤 동작까지 기록했다.

## 검증과 리뷰

- 실행 범위: 실제 대상. `tools/verify.py reused-cipher-memo`로 취약한 서버에서 solve가 flag를 회수하고, 패치 서버에서는 복원이 실패함을 확인했다(날짜는 검증 로그 참고).
- 기술 검증: 2026-10-14, `tools/verify.py reused-cipher-memo` 통과. `patched/test.sh`가 HELLO·MEMO 기본 동작, CHECK 반복 요청의 응답 차이, 복원 실패, 오류 응답을 모두 확인한다.
- 학습 리뷰: 아직 수행하지 않음. 배포 전 `challenge-reviewer` 스킬로 독립 학습 리뷰를 진행해야 한다.
- 맥락 확인: 처음 읽는 사람이 봉인지기·보관소·CHECK 점검 기능·조사할 일을 첫 메시지만으로 식별할 수 있는지 아직 `quality/text-reviews/reused-cipher-memo/`에서 확인하지 않았다.
- 용어 확인: 본문·힌트·해설이 모두 같은 명령 이름(HELLO, MEMO, CHECK)과 같은 표현(패드, 봉인)을 쓴다.
- 배포 준비 상태: 기술 검증만 완료. 학습 리뷰는 남아 있다.
