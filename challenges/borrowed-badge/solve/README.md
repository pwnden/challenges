## 조사 순서

1. `locker/team-notes`를 읽어 팀 공유 자료가 정상적으로 열리는지 확인한다.
2. 접근 규칙에서 `Action`이 `read`이고 `Resource`가 `locker/team-*`인 것을 확인한다.
   이 규칙은 이름이 `locker/team-`으로 시작하는 문서의 읽기를 허용한다.
3. 운영자의 복구 문서인 `locker/team-admin`도 같은 글자로 시작한다.
4. 이 전체 이름으로 읽기 요청을 보낸다.
5. 응답에 나타난 운영 복구 키 `pwnden{...}`를 제출한다.

개인 초안인 `locker/personal-draft`는 같은 정책에 맞지 않아 거절된다.
정상 요청과 거절 요청을 함께 비교하면 허용 규칙의 범위를 설명할 수 있다.

## 확인된 원리

서버는 읽기 요청을 받을 때 문서 이름을 접근 규칙과 비교한다.
`*`가 붙은 규칙은 공유 문서뿐 아니라 이름이 비슷한 운영자의 문서까지 허용했다.
목록의 '운영자 전용' 설명과 서버가 실제로 허용하는 범위가 달랐던 것이다.

## 고친 동작

수정한 규칙은 문서 이름이 정확히 `locker/team-notes`일 때만 읽기를 허용한다.
공유 노트는 계속 읽히고 운영자의 문서는 거절된다.
권한을 설정한 뒤에는 읽을 수 있어야 하는 문서와 제한해야 하는 문서를 각각 확인해야 한다.

이 실험에서는 사이트에 설명된 접근 규칙을 적용한다. 실제 클라우드 서비스에는
사용자·조직·문서별 규칙이 함께 적용될 수 있으므로, 최종적으로 누가 무엇을 할 수 있는지 확인해야 한다.
