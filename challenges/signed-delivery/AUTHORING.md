# 서명이 맞는 납품 문서 작성 기록

## 목표와 선수 능력

온전한서명은 납품 수신 담당자다. 항목이 다른 사본 중 승인 원문을 골라야 하며
발신자에게 확인한 공개키와 서명을 제공한다.

- 분야 `cryptographic-security`, 주제 `crypto-public-keys-signatures`, category `crypto`.
- teaches: 신뢰한 공개키의 서명 검증으로 내용 변경을 구분한다.
- requires `terminal-commands`, `detached-signatures`: 공개키·분리 서명·검증 성공/
  실패·확인 코드의 위치와 제출 방식은 브리핑에서 설명한다.
- 대상은 준비된 명령을 조정하는 초급자다. 난도 2는 여러 사본의 검증 결과와
  현재 승인본을 고르는 판단에 근거한다. 수학·개인키 생성·Python은 필요 없다.

## 자료 출처와 관찰

`authoring/build.py`는 길이가 같은 과거 승인본·현재 승인본·변경 사본을 만든다.
임시 디렉터리에서 RSA-2048 개인키를 생성해 PKCS#1 v1.5/SHA-256으로 서명하고
두 승인 버전을 같은 키로 각각 서명하고 공개키·서명만 배포한 뒤 개인키를 삭제한다.
신뢰한 승인 안내는 현재 배치·버전과 서명 대응 관계를 제공한다. 실제 업무 키는 없다.
생성 사본의 시각은 동일하게 설정한다. 파일명은 원문을 표시하지 않는다.

1. 신뢰한 키와 서명의 역할을 확인한다.
2. 과거 승인본도 유효하지만 현재 버전의 서명에는 현재 원문만 통과함을 확인한다.
3. 현재 승인본의 확인 코드를 그대로 제출한다. 세 사본의 코드는 서로 다르며 길이는 같다.

`authoring/check.py`는 실제 OpenSSL 검증으로 원문·변조 사본을 구분한다.
추가 1바이트 변경·서명 1바이트 변경·다른 공개키의 실패와 자료 재생성 후
같은 원문의 통과를 확인한다. 개인키 부재와 제출 코드의 정답 해시도
검사한다. 과거 승인본·변경 사본의 코드는 정답으로 인정하지 않는다. 해답은 CLI만
사용하고 검증한 사본이 정확히 하나일 때만 코드를 출력한다. 수동 후보 비교도 유효하다.

## 검증과 리뷰

### 2026-10-04 직접 제출 검증

세 문서에 길이가 같은 서로 다른 확인 코드를 넣고 서명을 다시 생성했다.
`python3 -B authoring/check.py`에서 현재 서명은 copy-c만, 과거 서명은 copy-b만
통과했다. 과거·변경 사본의 코드, 문서 1바이트 변경, 서명 1바이트 변경, 다른 키를
거부하는 검사와 자료 재생성 검사가 통과했다. 개인키는 배포 자료에 없다.
`python3 -B tools/verify.py hash-lantern signed-delivery`에서 실제 선언 이미지의
해답과 정리 검사가 통과했다. 해답은 현재 승인본의 확인 코드를 그대로 출력한다.
이 판본의 브라우저 제출·PTY 전체 풀이·실제 초보자 관찰은 별도로 수행하지 않았다.
