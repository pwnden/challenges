## 시나리오 설정

- 표시 제목: 안내 로봇의 메아리 기능

- 한 줄 소개: 로비 안내 로봇 관리자가 ECHO 기능으로 보호값이 새어나가 관리자 전용 출력까지 닿을 수 있는지 확인해 달라고 의뢰한다.
- 공개 닉네임과 말투: 문간지기. 자신이 관리하는 로봇의 두 기능을 정확히 설명하고, 보호값이 충분한지에 대한 불확실함을 솔직히 말한다.
- 의뢰인과 플레이어의 역할: 문간지기는 로봇 관리자, 플레이어는 ECHO·GREET 두 기능을 함께 시험하는 조사자다.
- 대상과 사건의 계기: 로비 안내 로봇 프로그램(ECHO 점검 기능, GREET 이름 입력 기능, 컴파일러가 넣은 보호값). ECHO와 보호값을 연결해 볼 수 있다는 이야기.
- 길드를 찾은 이유: 문간지기는 보호값이 변조를 막는다고만 알고 있었고, 그 값 자체가 다른 경로로 새어나갈 수 있는지는 직접 확인하지 못했다.
- 이번에 공개할 정보: 컴파일된 프로그램 파일과 접속 주소, 두 기능의 존재와 ECHO의 표시된 범위. "보호값"이 스택 카나리라는 용어나 정확한 오프셋은 공개하지 않는다.
- 의뢰 목표와 완료 증거: ECHO와 GREET를 함께 사용해 관리자 전용 출력(현재 flag)을 끌어냄. 새 연결에서 ECHO 요청 뒤 GREET 입력만으로 성공해야 한다.
- 처음 전달할 사실: 호스트·포트, 프로그램 파일, ECHO·GREET 두 단계 프로토콜.
- 사건의 흐름: 평소 동작(ECHO는 점검용, GREET은 보호값으로 지켜짐) → 제보(ECHO와 보호값을 연결해 볼 수 있다는 이야기) → 문간지기가 직접 확인하지 못함 → 조사 권한(프로그램 파일·접속 주소) 전달 → 실제로 관리자 전용 출력까지 닿을 수 있는지 조사.
- 조사 중 발견할 사실: ECHO가 화면의 범위를 넘는 요청도 받아들인다는 것, 그 초과분에 실행마다 달라지는 8바이트가 있다는 것, 그 바이트가 GREET의 보호값과 같은 자리에 있다는 것, 복귀 위치를 덮어쓸 수 있는 함수가 실행 파일 안에 이미 있다는 것.
- 풀이자에게 남긴 판단: ECHO의 실제 한계를 시험할지 여부, 실행마다 달라지는 구간을 찾는 방법, 정확한 오프셋 계산, 어느 함수로 복귀 위치를 돌릴지.
- 학습 목표와의 연결: 보호값은 "덮어쓰기 여부"만 확인하므로 정확한 값을 미리 알면 통과시킨다는 점과, 저장된 복귀 위치를 덮어써 이미 있는 함수로 실행을 돌릴 수 있다는 점을 직접 관찰한다.

## 학습 목표와 대상

- 현재 계약의 category: "pwn"
- 학습 분야: System security(`learning-map.md`) 중 `pwn-control-flow`와 `pwn-mitigations`의 경계 — "저장된 콜백/복귀 주소를 공급한 대상 함수로 돌린다"는 진입 사례와 "정보 유출이 특정 보호를 약화시킨다"는 사례를 함께 다룬다.
- 세부 주제: `pwn-control-flow`(복귀 주소 변조로 기존 함수 호출)를 중심으로, `pwn-mitigations`(보호값 우회에 정보 유출이 필요하다는 점)를 함께 체험한다.
- category 선택 근거: `vault-gate`(인접 변수 덮어쓰기)의 다음 단계로, 보호값이 있는 환경에서 제어 흐름을 바꾸는 문제라 `pwn`이 맞다.
- 보안 학습 목표: 스택 보호값은 변조 여부만 확인하므로, 다른 경로로 그 값이 새어나가면 공격자가 정확히 재현해 검사를 통과시킬 수 있고, 통과한 뒤에는 저장된 복귀 위치를 이미 있는 함수의 주소로 덮어써 새 코드 없이 실행을 돌릴 수 있다는 것을 설명할 수 있다.
- 확인할 보안 원리: 정보 유출에 의한 보호값 우회(`pwn-mitigations`)와 복귀 주소 제어(`pwn-control-flow`)의 결합.
- 대상 풀이자: `vault-gate`에서 다진 스택 레이아웃 읽기(`memory-layout`)에 더해, 두 번의 서로 다른 바이트열을 연결해 하나의 공격을 구성할 수 있는 풀이자. 디버거 사용은 요구하지 않는다.
- 시작 조건과 성공 증거: 프로그램 파일과 접속 주소가 주어진다. ECHO로 얻은 값을 GREET에 정확히 되돌려 관리자 전용 출력에서 현재 flag를 읽으면 성공이다.

## 의도된 풀이

| 단계 | 풀이자가 수행할 행동 | 발견·관찰할 내용 | 필요한 지식·도구 |
| --- | --- | --- | --- |
| 1 | ECHO에 64보다 큰 값을 요청해 본다 | 거부되지 않고 더 많은 바이트가 돌아옴 | 힌트 1 |
| 2 | 같은 요청을 반복해 어느 구간이 매번 달라지는지 비교한다 | 104번째 바이트부터 8바이트가 실행마다 다름 | 힌트 2 |
| 3 | `objdump -d -M intel files/kiosk`로 `main`을 읽는다 | ECHO 버퍼(rbp-0x70)·보호값(rbp-0x8)·이름 버퍼(rbp-0x50)의 오프셋, `nm`으로 찾은 `grant_access`의 실제 주소 | 힌트 3, `memory-layout` |
| 4 | 72바이트 채움 + leaked 보호값 8바이트 + 임의 8바이트 + `grant_access` 주소로 GREET에 접속한다 | "관리자 전용: pwnden{...}" | 해설 |

보안 학습 목표와의 연결: 2단계는 "보호값이 다른 경로로 새어나갈 수 있다"는 관찰을, 3~4단계는 "그 값을 정확히 되돌려주면 검사를 통과하고, 통과한 뒤에는 기존 함수로 실행을 돌릴 수 있다"는 결론을 직접 재현하게 한다.

풀이자의 언어 지식: 코드 작성은 필요 없다. ECHO 응답에서 정해진 구간을 잘라 GREET 입력에 다시 붙이는 바이트 조합만 필요하다. 두 단계를 하나의 연결로 이어 보내야 하므로 터미널 스크립트(Python 등)가 사실상 필요하다.

## 개념 관계

- 문제의 선수 개념: `memory-layout`(`vault-gate`가 가르침), `terminal-commands`.
- 문제의 학습 개념: `return-address-control`(`knowledge/return-address-control.md`) — 저장된 복귀 주소와 보호값.
- 개념 간 선수 관계: `return-address-control`은 `memory-layout`을 선수로 한다. 순환 없음.
- 관련 읽기: `vault-gate`(같은 pwn 계열의 이전 단계, 인접 변수 덮어쓰기만 다루고 보호값은 없음).
- 공개 위치: 프로그램 파일과 두 기능의 존재는 본문에서 공개. "보호값이 새어나간다"는 결론과 정확한 오프셋·함수 이름은 힌트·해설에서만 명시한다.

## 난도 근거

- 선언한 값: 3 (1 입문, 2 초급, 3 중급, 4 고급, 5 심화)
- 선수 지식 부담: `memory-layout`(이전 문제에서 다짐) 위에 보호값 개념을 새로 더한다.
- 발견 난도: 경계값 시험(ECHO 한계 확인) → 반복 비교(실행마다 달라지는 구간 찾기) → 오프셋 계산(두 버퍼와 보호값의 관계) → 두 단계를 하나의 공격으로 결합, 총 네 단계의 연결된 판단이 필요해 `vault-gate`(난도 2, 단일 오프셋 계산)보다 한 단계 더 복잡하다.
- 구현 부담: 코드 작성은 없지만 ECHO 응답의 특정 바이트 구간을 잘라 GREET 입력에 재조합하는 스크립트가 필요하다.
- 풀이 의존성: 2단계(보호값 위치 특정)가 3단계(오프셋 계산)의 전제이고, 3단계가 4단계(공격 조합)의 전제다.
- 등급 판정: `vault-gate`보다 한 단계(정보 유출 + 보호값 우회 + 제어 흐름 변조의 결합) 더 복잡해 난도 3이 적절하다.

manifest의 difficulty를 바꾸면 이 기록도 함께 갱신하세요.

## 다른 풀이와 정답 노출

- 확인한 다른 풀이: ECHO 요청 길이를 104보다 큰 임의의 값(최대 120)으로 바꿔도 같은 방식으로 성공함을 확인했다. 디스어셈블리 없이 반복 요청만으로 "실행마다 달라지는 8바이트" 구간을 찾는 블랙박스 풀이도 같은 결론(보호값 위치)에 이른다.
- 의도치 않은 지름길 점검: ECHO 응답은 정답 형식의 고정 문자열을 포함하지 않으며, 보호값은 매 실행 무작위라 이전 실행의 값을 재사용할 수 없다.
- 본문 노출 점검: 본문은 ECHO·GREET 두 기능의 존재와 ECHO의 표시된 범위만 제공하고, 두 기능을 연결해야 한다는 것이나 정확한 오프셋은 말하지 않는다. 파일을 그대로 실행하거나 짧은 ECHO 요청만으로는 목표에 도달할 수 없다.
- 필요한 힌트: 1번은 ECHO 한계 시험, 2번은 반복 비교로 보호값 구간을 찾는 방법, 3번은 objdump로 오프셋과 대상 함수를 찾는 방법을 각각 제공한다. 본문만으로는 ECHO의 실제 한계를 의심할 단서가 부족해 3개를 유지한다.
- 해설: `solve/README.md`에 ECHO 초과 읽기 확인, objdump 오프셋 계산, 공격 조합, 패치 뒤 동작까지 기록했다.

## 검증과 리뷰

- 실행 범위: 실제 대상. 컴파일된 `files/kiosk`를 `python:3.13.15-slim-trixie` 기반 컨테이너에서 9회 반복 실행해 보호값 하위 바이트가 항상 0x00임과 공격이 매번 성공함을 확인했고, 실제 TCP 서비스(`docker compose`)에 대해서도 같은 공격이 성공함을 확인했다. `tools/verify.py greeting-echo`로 취약한 서버에서 solve가 flag를 회수하고 패치 서버에서는 거부됨을 확인했다.
- 기술 검증: 2026-10-14, `objdump`로 확인한 오프셋(ECHO 버퍼=rbp-0x70, 보호값=rbp-0x8, 이름 버퍼=rbp-0x50, 차이 104/72)과 `nm`으로 확인한 `grant_access` 주소(0x4011b6)가 실제 공격 성공과 일치함을 확인했다. 컴파일에 쓰는 Debian 패키지 스냅샷을 `vault-gate`와 같은 방식으로 고정해 오프셋이 빌드마다 바뀌지 않음을 확인했다. `tools/verify.py greeting-echo` 통과. `patched/test.py`가 평소 사용·경계값(64바이트)·이전 120바이트 요청·음수 요청을 모두 확인한다. 이후 `night-console`을 만들며, 연결을 받는 Python 계층이 첫 줄을 버퍼링된 스트림으로 읽은 뒤 이어지는 입력을 raw 소켓으로 읽으면 클라이언트가 두 메시지를 한 번에 보낼 때 뒤쪽 바이트가 버려지는 결함을 발견해 이 문제의 `vulnerable/app.py`도 모든 읽기를 같은 버퍼링된 스트림으로 통일했다(이 결함은 응답을 기다린 뒤 보내는 클라이언트에서는 드러나지 않았다). 수정 뒤 `tools/verify.py greeting-echo`를 다시 통과시켰다.
- 학습 리뷰: 미완료(독립 리뷰어 관찰 필요).
- 리뷰 관찰: 미완료.
- 맥락 확인: 처음 읽는 사람이 문간지기·안내 로봇·ECHO/GREET 기능·조사할 일을 첫 메시지만으로 식별할 수 있는지 `quality/text-reviews/greeting-echo/`에서 확인한다.
- 용어 확인: 본문·힌트·해설이 모두 같은 기능 이름(ECHO, GREET)과 같은 응답 문구("관리자 전용", "환영합니다")를 쓴다.
- 배포 준비 상태: 기술 검증 통과. 학습 리뷰(독립 관찰)는 아직 비어 있어 배포 전 보완이 필요하다.
