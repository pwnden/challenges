:person[노을책갈피]는 작은 문서 서비스의 운영 담당자다. 손님은 자신의 회의 메모를 읽고
JSON 사본으로 내려받을 수 있다. 손님은 운영 담당자의 복구 절차 문서를 읽어서는
안 된다. 그 문서에는 서비스를 복구할 때 쓰는 비밀 코드가 들어 있다.

서비스에 문서 내보내기 기능을 새로 추가했다. 문서를 일반 조회로 요청하면 서버가
다른 사람의 문서를 읽지 못하게 막는다. 하지만 내보내기 기능에서도 같은 권한을
검사하는지는 아직 확인하지 않았다.
운영자는 길드에 실습용 손님 계정과 문서 목록을 제공하고 두 작업의 차이를
확인해 달라고 요청했다. 서버와 계정은 이 문제의 격리 환경 안에서만 사용한다.

::objective
같은 문서를 일반 조회와 내보내기로 요청해 권한을 비교하고, 잘못 공개된 복구 코드를 찾자.
::

::resources{title="실습 계정과 API"}
- 터미널의 서비스 주소는 `http://app:8000`이다.
- 로그인은 `POST /api/login`, 계정은 `guest`, 비밀번호는 `lab-guest`다.
- `GET /api/catalog`는 문서의 ID·소유자·제목만 보여 준다.
- `GET /api/notes/문서ID`는 본문 조회다.
- `POST /api/exports`에 `{"note_id":문서ID}`를 보내면 기본 요약 사본을 요청한다.
- `GET /`에는 제공하는 작업과 내보내기 형식의 안내가 있다.

먼저 로그인 쿠키를 저장하고 목록과 자기 문서를 읽자.

```sh
curl -sS -c cookies.txt -H 'Content-Type: application/json' \
  -d '{"username":"guest","password":"lab-guest"}' http://app:8000/api/login
curl -sS -b cookies.txt http://app:8000/api/catalog | jq .
curl -i -b cookies.txt http://app:8000/api/notes/7
```

자기 문서의 정상 동작을 확인한 뒤, 목록에서 다른 소유자의 문서를 골라 두 작업을
비교하자. 쿠키와 응답 파일은 문제를 종료하면 지워지는 임시 공간에 저장된다.
요약 사본은 제목·소유자만 담을 수 있다. 상태가 200이어도 실제 본문이 제공됐는지
확인하고, 형식에 따라 반환 내용과 권한 검사가 달라지는지 비교하자.

### 준비된 터미널 명령 사용하기

터미널에는 한 줄의 명령을 입력하고 Enter를 누르면 된다. `files/`로 시작하는
경로는 이 문제의 배포 파일을 가리킨다. 명령 예제의 파일명은 조사할 자료의 이름으로 바꿔 넣자.

`printf '%s' 'hello'`는 줄바꿈 없이 `hello`를 출력한다.
`|`는 왼쪽 출력물을 오른쪽 프로그램의 입력으로 전달한다.
예를 들어 `printf '%s' 'hello' | sha256sum`은 정확히 다섯 글자를 해시한다.
`hello` 뒤에 줄바꿈이 추가되면 해시도 달라진다.

각 문제의 ‘전달받은 자료’에서 파일을 읽고 결과를 확인할 명령을 안내한다.
Ctrl+C는 오래 실행되는 명령을 중단하고, 위쪽 화살표는 이전 명령을 다시 가져온다.

### Web 요청과 응답 읽기

사이트에서 버튼을 누르거나 주소를 열면 브라우저는 서버에 **요청**을 보내고,
서버는 상태와 내용을 담은 **응답**을 돌려준다. `GET`은 자료 조회에 흔히 쓰이는 요청 방식이다.

예를 들어 `GET /help`는 도움말을 요청한다. 응답의 `200`은 요청 성공,
`403`은 접근 거절, `404`는 찾을 수 없는 자료를 뜻한다. 화면에 오류 안내가 뜨면
입력한 값과 응답 내용을 함께 살펴보자. 상태 번호만으로 자료의 내용까지 알 수는 없다.

**헤더**는 쿠키나 내용 형식 같은 부가 정보다. **본문**은 페이지, 문서, 데이터 자체다.
같은 주소라도 요청에 실린 정보에 따라 서버가 다른 내용을 돌려줄 수 있다.

### 쿠키와 신원

쿠키는 브라우저가 보관했다가 사이트로 다시 보내는 작은 `이름=값` 데이터다.
`theme=dark`처럼 표시 설정을 담기도 하고, 로그인 상태를 이어 가는 데 쓰이기도 한다.

쿠키를 담은 요청은 대략 `Cookie: theme=dark`처럼 보인다. 여기서 `theme`은 이름,
`dark`는 값이다. 값이 `light`로 바뀌면 서버가 받는 요청 정보도 달라진다.

쿠키가 어디에서 왔고 어떤 권한을 나타내는지는 서버가 확인해야 한다.
브라우저가 전달한 글자만으로 그 사용자의 신원과 권한이 증명되지는 않는다.
**세션**은 로그인한 상태를 이어 가기 위한 정보다. 서버에 저장한 사용자 정보를
브라우저의 세션 식별자로 찾아보거나, 서버가 만든 값이 바뀌지 않았는지 검사하는 방식으로 관리한다.

### curl로 JSON API 읽기

API는 프로그램이 사용하는 요청 창구다. `curl -sS 주소`는 응답 본문을 읽고,
`-i`를 더하면 상태와 헤더도 보여 준다. JSON은 이름과 값으로 데이터를 표현한다.
예를 들어 `printf '%s' '{"note":{"id":3}}' | jq '.note.id'`는 숫자 3을 읽는다.

`curl -H 'Content-Type: application/json' -d '{"note_id":3}' 주소`는 JSON 본문을
보내는 POST 요청이다. `note_id`는 이 예제에서 작업 대상 문서의 ID를 뜻한다.
같은 문서를 읽는 GET 요청과 사본을 만드는 POST 요청은 서로 다른 작업이다.

로그인 응답의 쿠키를 저장하려면 `-c cookies.txt`, 이후 요청에 보내려면
`-b cookies.txt`를 사용한다. 쿠키는 서버가 로그인 상태를 이어서 확인하는 값이다.
JSON 본문을 바꿔도 로그인한 사용자와 서버가 보관한 문서 소유자가 바뀌지는 않는다.

상태만 확인할 때는 `-o reply.json -w '%{http_code}\n'`을 쓴다. 본문은 파일에
저장하고 상태는 화면에 표시한다. 200은 처리 성공, 401은 로그인 필요,
403은 권한 거부다. 상태와 실제 본문을 함께 비교하자.
