## 시나리오 설정

- 표시 제목: 노크 순서로 여는 유지보수 게이트

- 한 줄 소개: 포트 노크로 보호한 유지보수 게이트 관리자가 순서를 지키지 않은 접속 뒤에도 게이트가 열린 기록을 조사해 달라고 의뢰한다.
- 공개 닉네임과 말투: 빗장당번. 차분하고 실무적인 말투로 자신이 관리하는 게이트의 설정과 관찰한 사실만 보고한다.
- 의뢰인과 플레이어의 역할: 빗장당번은 게이트 관리자, 플레이어는 접속 기록을 재현하는 조사자다.
- 대상과 사건의 계기: 포트 노크로 보호한 유지보수 게이트. 순서를 지키지 않은 접속 묶음 뒤에도 게이트가 열린 기록이 남음.
- 길드를 찾은 이유: 빗장당번은 실제 순서를 모르는 채로 운영만 해 왔고, 그 기록이 정말 순서를 어긴 접속인지 직접 재현해 보지 못했다.
- 이번에 공개할 정보: 대상 호스트, 노크 포트 범위, 게이트 주소와 응답 형식. 서버가 진행 상태를 어떻게 저장하는지(집합인지 단계인지)는 공개하지 않는다.
- 의뢰 목표와 완료 증거: 게이트가 순서를 실제로 확인하는지 확인하고 현재 flag를 읽는다. 노크 포트 세 개에 아무 순서로나 한 번씩 접속한 뒤 게이트에 접속해도 flag를 얻으면 완료다.
- 처음 전달할 사실: 대상 호스트, 노크 포트 범위(7001–7003), 게이트 주소(`app:7000`)와 그 응답 형식.
- 사건의 흐름: 평소에는 정해진 순서로만 열린다고 알려짐 → 접속 기록에 순서를 지키지 않은 흔적이 남음 → 빗장당번이 직접 재현 못 함 → 조사 권한(호스트·포트 범위·게이트 주소) 전달 → 순서 확인 여부 조사.
- 조사 중 발견할 사실: 노크 포트 세 개에 접속한 순서와 무관하게, 세 포트 모두에 접속한 뒤에는 게이트가 열린다는 비교.
- 풀이자에게 남긴 판단: 어떤 순서 조합을 시도할지, 게이트의 응답을 어떻게 비교해 "순서를 확인하지 않는다"는 결론을 세울지.
- 학습 목표와의 연결: 단일 연결의 상태 추적(`connection-state`)을 넘어, 서로 다른 연결 여러 개를 하나의 순서로 묶어 확인하는 구현이 실제로 그 순서를 강제하는지 직접 관찰한다.

## 학습 목표와 대상

- 현재 계약의 category: "misc"
- 학습 분야: System/Network security 중 다단계 접근 제어 — 여러 연결에 걸친 순서를 선언한 규칙이 실제로 그 순서를 강제하는지 확인하는 체험.
- 세부 주제: 포트 노크처럼 "여러 단계를 정해진 순서로 거쳐야 한다"는 규칙이 단계의 집합만 확인하도록 잘못 구현된 사례.
- category 선택 근거: 기존 misc 분류(`backup-relay`, `diagnostic-port`)와 같은 포트·TCP 조사 범주이며, `web`·`pwn`·`rev`·`crypto`·`forensics`에 맞지 않는 순수 TCP 프로토콜 문제다.
- 보안 학습 목표: 여러 연결에 걸친 순서 확인이 번호가 매겨진 단계로 구현되는지, 아니면 단계의 집합으로만 구현되는지를 구분하고, 후자가 순서 보호를 사실상 무력화한다는 것을 설명할 수 있다.
- 확인할 보안 원리: 다단계 접근 제어에서 "모든 단계를 거쳤는가"와 "정해진 순서로 거쳤는가"를 혼동한 구현 결함.
- 대상 풀이자: 터미널에서 `ncat`으로 여러 TCP 포트에 접속하고, `nmap`으로 포트 범위를 조사할 수 있는 풀이자. `tcp-services`와 `connection-state` 선수 지식을 가정한다.
- 시작 조건과 성공 증거: 대상 호스트, 노크 포트 범위, 게이트 주소가 주어진다. 노크 포트 세 개에 어떤 순서로든 접속한 뒤 게이트에 접속해 `pwnden{...}`를 받으면 성공이다.

## 선수 지식과 학습 내용

| 필요한 능력 | 역할: 선수 지식 / 학습 목표 / 배경 | 필요한 풀이 단계 | 제공 위치: 개념 자료 / 본문 / 힌트 / 해설 |
| --- | --- | --- | --- |
| 터미널에서 ncat으로 여러 TCP 포트에 접속한다 | 선수 지식 | 전체 | 개념 자료(`tcp-services`) |
| 한 연결 안에서 서버가 상태를 기억할 수 있음을 안다 | 선수 지식 | 배경 | 개념 자료(`connection-state`) |
| 접속 순서를 바꿔 가며 게이트 응답을 비교한다 | 학습 목표 | 2단계 | 본문 + 힌트 1 |
| 순서를 신경 쓰지 않고 세 포트를 모두 노크한 뒤 게이트를 시도 | 학습 목표 | 3단계 | 힌트 2 + 해설 |

## 의도된 풀이

| 단계 | 풀이자가 수행할 행동 | 발견·관찰할 내용 | 필요한 지식·도구 |
| --- | --- | --- | --- |
| 1 | 노크 없이 바로 `app:7000`에 접속한다 | `DENIED not_unlocked` 응답 확인 | `tcp-services` |
| 2 | 노크 포트 세 개에 서로 다른 순서로 접속해 보며 게이트 응답을 비교한다 | 순서를 바꿔도 세 포트를 모두 거치면 같은 결과가 나올 가능성을 포착 | 힌트 1 |
| 3 | 순서를 신경 쓰지 않고 세 포트에 한 번씩 접속한 뒤(또는 `nmap`으로 범위를 훑은 뒤) 게이트에 접속한다 | `OK pwnden{...}` 응답, 순서가 실제로는 확인되지 않음을 확인 | 힌트 2 + 해설 |

보안 학습 목표와의 연결: 1단계는 게이트가 기본적으로 잠겨 있다는 사실을 세우고, 2–3단계는 "세 단계를 모두 거쳤는가"만으로 열린다는 결함을 직접 관찰하게 한다.

풀이자의 언어 지식: 코드 작성이나 읽기는 필요 없다. 여러 포트에 접속하는 순서를 바꿔 가며 응답을 비교하는 것만으로 충분하다.

## 개념 관계

- 문제의 선수 개념: `terminal-commands`, `tcp-services`(`knowledge/tcp-services.md`), `connection-state`(`knowledge/connection-state.md`).
- 문제의 학습 개념: `knock-sequence-trust`(`knowledge/knock-sequence-trust.md`) — 여러 연결에 걸친 순서 확인.
- 개념 간 선수 관계: `knock-sequence-trust`는 `tcp-services`와 `connection-state`를 선수로 한다. 순환 없음.
- 관련 읽기: `backup-relay`(한 연결 안의 상태 확인 누락을 다루는 같은 misc 분류 문제. 이 문제는 그 상태 확인을 여러 연결로 확장한다).
- 공개 위치: 노크 포트 범위와 게이트 주소는 본문에서 공개. 실제로 필요한 순서(7003 → 7001 → 7002)와 서버가 집합으로만 확인한다는 결함은 힌트·해설에서만 명시한다.

## 난도 근거

- 선언한 값: 3 (1 입문, 2 초급, 3 중급, 4 고급, 5 심화)
- 선수 지식 부담: `tcp-services`와 `connection-state` 둘을 모두 요구하며, 노크 프로토콜 자체는 본문이 설명한다.
- 발견 난도: 한 연결의 상태 확인(`backup-relay`)을 넘어, 여러 개의 서로 다른 연결을 하나의 순서로 묶어 생각해야 하고, "집합인지 순서인지"를 스스로 가설을 세워 시험해야 한다.
- 구현 부담: 코드 작성 없이 여러 번의 `ncat` 접속 조합만 필요하다.
- 풀이 의존성: 2단계(순서를 바꿔 본 관찰)가 3단계(순서 무시 시도)의 가설을 만든다.
- 등급 판정: `backup-relay`(2, 한 연결 안의 상태 확인 누락)보다 여러 연결에 걸친 순서라는 개념 한 겹이 더해져 중급(3)으로 둔다.

manifest의 difficulty를 바꾸면 이 기록도 함께 갱신하세요.

## 다른 풀이와 정답 노출

- 확인한 다른 풀이: 노크 포트를 내림차순(7003, 7002, 7001)으로 접속해도 동일하게 성공함을 `solve.py`를 변형해 확인했다(집합 확인은 순서 자체에 무관하므로 당연한 결과다).
- 의도치 않은 지름길 점검: 노크 포트에 데이터 없이 접속만 해도 되므로, 플레이어가 `nmap`의 기본 TCP 연결 스캔(`-sT`)만으로 노크 포트 범위를 훑어도 동일하게 성공한다. 이는 의도한 풀이 경로이며 지름길이 아니다.
- 본문 노출 점검: 본문은 노크 포트 범위와 게이트 주소만 제공하고, 서버가 순서를 집합으로만 확인한다는 사실이나 실제 필요한 순서는 말하지 않는다. 본문만 읽고 "정해진 순서"를 추측해 시도하면 실패하는 정상 경로가 먼저 재현되고, 순서 무시 시도는 플레이어가 직접 해야 한다.
- 필요한 힌트: 1번은 순서를 바꿔 비교해 보라는 방향을, 2번은 순서를 무시한 구체적 시도를 제공한다. 본문만으로는 "순서가 집합으로만 확인될 수 있다"는 가설을 세울 단서가 부족해 2개를 유지한다.
- 해설: `solve/README.md`에 전체 재현, 결함의 원인, 패치 뒤 동작까지 기록했다.

## 검증과 리뷰

- 실행 범위: 실제 대상. `tools/verify.py knock-sequence-gate`로 취약한 서버에서 solve가 flag를 회수하고, 패치 서버에서는 거부됨을 확인했다(날짜는 검증 로그 참고).
- 기술 검증: 2026-10-14, `tools/verify.py knock-sequence-gate` 통과. `patched/test.sh`가 노크 전 거부, 그럴듯한 오름차순 추측의 거부, 실제 순서(7003 → 7001 → 7002)의 성공을 모두 확인한다.
- 학습 리뷰: 아직 수행하지 않음. 배포 전 `challenge-reviewer` 스킬로 독립 학습 리뷰를 진행해야 한다.
- 맥락 확인: 처음 읽는 사람이 빗장당번·게이트·순서를 어긴 접속 기록·조사할 일을 첫 메시지만으로 식별할 수 있는지 아직 `quality/text-reviews/knock-sequence-gate/`에서 확인하지 않았다.
- 용어 확인: 본문·힌트·해설이 모두 같은 이름(노크 포트, 게이트, `DENIED not_unlocked`, `OK pwnden{...}`)을 쓴다.
- 배포 준비 상태: 기술 검증만 완료. 학습 리뷰는 남아 있다.
