## 조사 결과

게이트는 "노크한 포트의 집합"만 확인했다. 어떤 순서로 접속했는지는 전혀
확인하지 않았으므로, 노크 포트 세 개(7001–7003)에 아무 순서로나 한 번씩만
접속한 뒤 게이트에 접속하면 열렸다. `nmap`으로 그 범위를 그냥 훑기만 해도
세 포트 모두에 접속이 일어나므로 같은 결과가 나온다.

## 조사 과정

노크 포트 하나에 접속한 뒤 바로 끊어도 그 포트는 "노크됨"으로 기록된다.
접속 순서를 여러 조합으로 바꿔 가며 시험해 보면, 순서와 무관하게 세 포트에
모두 접속한 뒤에는 게이트(`app:7000`)가 `DENIED not_unlocked` 대신
`OK pwnden{...}`를 돌려준다는 사실을 관찰할 수 있다. 접속 기록에 남아 있던
"순서를 지키지 않은 묶음"도 바로 이 경로였다.

## 의뢰 완료 확인

`solve/solve.py`는 노크 포트 세 개를 오름차순(7001 → 7002 → 7003, 운영자가
설명한 '정해진 순서'와는 무관한 임의의 순서)으로 접속한 뒤 게이트에 접속해
flag를 그대로 출력한다.

## 드러난 보안 원리

"정해진 순서로 접속해야 한다"는 규칙을 구현할 때, 실제로 번호가 매겨진
단계로 순서를 확인하는지와 "그 단계들을 모두 거쳤는가"라는 집합으로만
확인하는지는 서로 다른 구현이다. 집합으로 확인하면 순서는 더 이상 보호
수단이 아니며, 포트 범위를 스캔하는 것만으로도 모든 단계를 우연히 거치게
된다.

패치한 서버는 노크마다 "지금 기대하는 다음 포트"를 번호가 매겨진 단계로
확인하고, 기대와 다른 포트가 오면 진행 상태를 되돌린다. 실제로 필요한 순서는
7003 → 7001 → 7002이며, `patched/test.sh`는 이 순서로만 게이트가 열리고
오름차순 같은 그럴듯한 추측은 더 이상 통하지 않음을 확인한다.
