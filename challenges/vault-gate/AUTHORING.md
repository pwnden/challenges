## 시나리오 설정

- 표시 제목: 방문자 접수대의 입력 한계

- 한 줄 소개: 방문자 접수대 프로그램 관리자가 긴 이름 입력으로 직원 전용 자료가 나왔다는 제보를 조사해 달라고 의뢰한다.
- 공개 닉네임과 말투: 문지기. 자신이 관리하는 프로그램의 동작을 정확하지만 담백하게 설명하고, 재현하지 못한 부분을 솔직히 인정한다.
- 의뢰인과 플레이어의 역할: 문지기는 접수대 프로그램 관리자, 플레이어는 제보를 외부에서 재현하는 조사자다.
- 대상과 사건의 계기: 사무실 방문자 접수대 프로그램(이름 입력 → 인사말, 내부 직원 여부 값에 따라 직원 전용 자료 표시). 팀원이 긴 이름 입력으로 직원 전용 자료를 봤다는 제보.
- 길드를 찾은 이유: 문지기가 직접 재현하지 못했고, 프로그램의 실제 메모리 동작까지는 분석할 수 없었다.
- 이번에 공개할 정보: 컴파일된 프로그램 파일과 접속 주소. 소스 코드나 `is_staff`라는 변수 이름은 공개하지 않는다.
- 의뢰 목표와 완료 증거: 이름 입력만으로 직원 전용 자료를 띄우고 그 안의 현재 flag를 제출. 새 연결에서 이름 한 줄만 보내도 성공해야 한다.
- 처음 전달할 사실: 호스트·포트, 프로그램 파일, 한 줄 프로토콜(이름+줄바꿈 → 응답 후 연결 종료).
- 사건의 흐름: 평소 동작(이름 입력 → 인사말, 직원 여부는 내부에서만 설정됨) → 제보(긴 이름으로 직원 전용 자료가 나옴) → 문지기가 재현 실패 → 조사 권한(프로그램 파일·접속 주소) 전달 → 실제로 이름 입력만으로 재현 가능한지 조사.
- 조사 중 발견할 사실: 디스어셈블리로 확인하는 `name`과 `is_staff`의 스택 오프셋 차이, 그리고 `fgets`가 받아들이는 실제 크기.
- 풀이자에게 남긴 판단: 어떤 길이의 입력을 시도할지, 디스어셈블리를 읽을지 블랙박스로 길이를 늘려 갈지, 정확한 오프셋을 어떻게 계산할지.
- 학습 목표와의 연결: 선언된 배열 크기보다 긴 쓰기가 "바로 옆 변수의 메모리"를 바꾼다는 것을 직접 관찰하고 계산한다.

## 학습 목표와 대상

- 현재 계약의 category: "pwn"
- 학습 분야: System security(`learning-map.md`) 중 `pwn-memory-boundaries` — "A write beyond a buffer's bounds can affect neighboring state"의 입문 진입 사례("An adjacent permission value changes")를 그대로 따른다.
- 세부 주제: `pwn-memory-boundaries`.
- category 선택 근거: 메모리 경계를 벗어난 쓰기가 인접 상태를 바꾸는 문제로, 계약이 정의한 `pwn` 분류에 해당하며 저장소 최초의 `pwn` 문제다.
- 보안 학습 목표: 배열에 선언된 크기보다 긴 쓰기가 허용되면 인접한 변수의 값을 바꿀 수 있고, 그 위치는 소스가 아니라 실제 컴파일 결과로 확인해야 한다는 것을 설명할 수 있다.
- 확인할 보안 원리: 크기 검사 결함으로 인한 인접 스택 변수 덮어쓰기(`pwn-memory-boundaries`).
- 대상 풀이자: 터미널에서 컴파일된 실행 파일을 `file`·`objdump`로 읽고, TCP로 접속해 바이트 단위 입력을 보낼 수 있는 풀이자. `program-reading` 선수 지식을 가정한다. 디버거 사용은 요구하지 않는다.
- 시작 조건과 성공 증거: 프로그램 파일과 접속 주소가 주어진다. 이름 입력만으로(코드 실행이나 셸 획득 없이) 직원 전용 자료에서 현재 flag를 읽으면 성공이다.

## 의도된 풀이

| 단계 | 풀이자가 수행할 행동 | 발견·관찰할 내용 | 필요한 지식·도구 |
| --- | --- | --- | --- |
| 1 | `app:9100`에 접속해 짧은 이름을 보낸다 | "손님 접근만 허용됩니다." 응답, 정상 동작 확인 | `terminal-commands` |
| 2 | 입력 길이를 조금씩 늘려 가며 비교한다 | 77바이트 이하는 손님, 78바이트부터 직원 전용 자료로 바뀌는 경계 발견 | 힌트 1 |
| 3 | `objdump -d -M intel files/vault`로 `main`을 읽는다 | `name`(rbp-0x50)과 `is_staff`(rbp-0x4)의 오프셋 차이(76)와 `fgets`가 받는 크기(256)를 확인하되, 뒤이은 trim 코드가 찾은 줄바꿈 위치에 다시 NUL을 쓰므로 실제 경계는 76이 아니라 77임을 접속 시험으로 함께 확인 | 힌트 2, `program-reading` |
| 4 | 77바이트 채움 + 줄바꿈으로 접속해 flag를 읽는다 | "직원 전용 자료: pwnden{...}" | 해설 |

보안 학습 목표와의 연결: 2단계의 블랙박스 관찰(경계값 발견)과 3단계의 화이트박스 확인(오프셋 계산)이 같은 결론으로 수렴하는 것을 보여 준다. 디버거 없이도 디스어셈블리만으로 "어느 변수가 얼마나 겹치는가"를 계산할 수 있음을 체험한다.

풀이자의 언어 지식: 코드 작성은 필요 없다. `objdump` 출력을 읽고 두 오프셋의 차이를 계산하는 것, 그리고 TCP로 정해진 길이의 바이트를 보내는 것만 필요하다.

## 개념 관계

- 문제의 선수 개념: `terminal-commands`, `program-reading`.
- 문제의 학습 개념: `memory-layout`(`knowledge/memory-layout.md`) — 지역 변수의 메모리 배치.
- 개념 간 선수 관계: `memory-layout`은 `program-reading`과 `terminal-commands`를 선수로 한다. 순환 없음.
- 관련 읽기: 없음(저장소 최초의 `pwn` 문제).
- 공개 위치: 프로그램 파일과 접속 방법은 본문에서 공개. 정확한 경계 길이(77/78)와 어느 변수가 겹치는지는 힌트·해설에서만 명시한다.

## 난도 근거

- 선언한 값: 2 (1 입문, 2 초급, 3 중급, 4 고급, 5 심화)
- 선수 지식 부담: `program-reading`만 있으면 되고, 디버거나 ROP 등 추가 도구는 필요 없다.
- 발견 난도: 길이를 늘려 가는 블랙박스 관찰만으로도 경계를 찾을 수 있고, 디스어셈블리는 그 경계를 설명하는 보조 확인이다. 입문보다 한 단계의 추론(경계값 탐색 또는 오프셋 계산)이 더 필요하다.
- 구현 부담: 코드 작성 없이 고정 길이의 바이트를 조합해 보내는 것으로 충분하다.
- 풀이 의존성: 2단계(경계 발견)와 3단계(오프셋 계산)는 같은 결론에 이르는 서로 다른 경로이며, 어느 한쪽만으로도 4단계에 도달할 수 있다.
- 등급 판정: ASLR·스택 카나리·주소 유출이 필요 없는 가장 단순한 인접 변수 덮어쓰기로, `pwn` 분류의 입문 바로 위 등급에 해당한다.

manifest의 difficulty를 바꾸면 이 기록도 함께 갱신하세요.

## 다른 풀이와 정답 노출

- 확인한 다른 풀이: 디스어셈블리 없이 78, 80, 200바이트 등 다양한 길이를 직접 시도해 경계를 찾는 블랙박스 풀이도 동일한 목표(인접 변수 덮어쓰기)를 관찰하며, `solve.py`가 사용하는 최소 길이(78바이트, A 77개+줄바꿈)와 같은 결론에 이른다.
- 의도치 않은 지름길 점검: flag 형식만 검색해 추측할 수 있는 고정 문자열이 응답에 없는지 확인했다. "직원 전용 자료" 응답은 매 실행 생성되는 flag를 포함할 때만 나타난다.
- 본문 노출 점검: 본문은 프로그램 파일과 접속 방법만 제공하고 정확한 오프셋이나 변수 이름은 말하지 않는다. 파일을 그대로 실행하거나 짧은 이름만 보내서는 목표에 도달할 수 없다.
- 필요한 힌트: 1번은 길이를 늘려 가는 탐색 방향을, 2번은 디스어셈블리로 오프셋을 계산하는 구체적 방법을 제공한다. 본문만으로는 입력 길이가 중요하다는 단서가 부족해 2개를 유지한다.
- 해설: `solve/README.md`에 디스어셈블리 발췌, 오프셋 계산, 실제 경계값 확인, 패치 뒤 동작까지 기록했다.

## 검증과 리뷰

- 실행 범위: 실제 대상. 컴파일된 `files/vault`를 `python:3.13.15-slim-trixie` 기반 컨테이너에서 직접 실행해 77바이트 이하/78바이트 경계를 확인했고, `tools/verify.py vault-gate`로 취약한 서버에서 solve가 flag를 회수하고 패치 서버에서는 거부됨을 확인했다.
- 기술 검증: 2026-10-14, `objdump`로 확인한 오프셋(name=rbp-0x50, is_staff=rbp-0x4, 차이 76)만으로는 경계를 다 설명하지 못해 실제 접속 시험으로 보완했다. trim 코드가 찾은 줄바꿈 위치에 다시 NUL을 쓰기 때문에 실제 경계는 77바이트 이하는 손님, 78바이트부터 직원이다. 컴파일에 쓰는 Debian 패키지 스냅샷을 `images/cli/Dockerfile`과 같은 방식으로 고정해 이 경계가 빌드마다 바뀌지 않음을 확인했다(스냅샷 고정 전에는 76/77 경계가 빌드마다 달랐다). `tools/verify.py vault-gate` 통과. `patched/test.py`가 평소 이름·경계값(63바이트)·이전 overflow payload(77바이트 A+줄바꿈)·200바이트 이름을 모두 확인한다.
- 학습 리뷰: 2026-10-14, 3인 패널(초급 학습자 관점·증거 검토자·교육 설계자, claude-sonnet-5-5 low effort; 사용자 승인에 따라 스킬이 정한 gpt-6-luna의 대체). 기준표 가중 합산 78.13/100. `needs_adjudication` 없음, 5인 확대 조건 미충족. 감사 기록: `quality/panels/vault-gate/2026-10-14-panel.json`.
- 리뷰 관찰: 세 심사자 모두 해설(`solve/README.md`)이 "디스어셈블리의 오프셋 차이(76)만으로는 끝이 아니고, 뒤이은 trim 코드가 같은 바이트를 다시 쓴다"는 한계까지 설명한 점을 가장 높게 평가했다(explanation 3~4, reasoning 3~4). 공통 간극은 `terminal-commands.md`에 `ncat`으로 TCP 서비스에 접속하는 구체적 예시가 없어 첫 접속 명령을 스스로 구성해야 한다는 점(starting_context 3)과, 기술 검증이 저자가 기록한 날짜 있는 실행(`tools/verify.py`, 2026-10-14)의 인용이며 심사자가 직접 재실행한 기록은 아니라는 점(execution 2~3)이다.
- 맥락 확인: 처음 읽는 사람이 문지기·접수대 프로그램·제보·조사할 일을 첫 메시지만으로 식별할 수 있는지 `quality/text-reviews/vault-gate/`에서 확인한다.
- 용어 확인: 본문·힌트·해설이 모두 같은 응답 문구("손님 접근만 허용됩니다.", "직원 전용 자료")를 쓴다.
- 배포 준비 상태: 기술 검증과 학습 리뷰 모두 통과. 패널이 공통으로 지적한 `ncat` 접속 예시 부재는 배포 전 보완을 권고하는 개선 사항으로 남아 있으나, 배포를 막는 결함(needs_adjudication)은 없다.
