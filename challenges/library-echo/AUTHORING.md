## 시나리오 설정

- 표시 제목: 안내 단말기의 되묻는 인사말

- 한 줄 소개: 안내소 단말기 관리자가 긴 이름 입력 뒤 단말기가 스스로 다시 시작하는 것처럼 보였다는 제보를 조사해 달라고 의뢰한다.
- 공개 닉네임과 말투: 서가지기. 관찰한 현상(알아볼 수 없는 글자, 다시 시작한 것 같은 동작)을 사실 그대로 전달하고, 원인은 모른다고 솔직히 말한다.
- 의뢰인과 플레이어의 역할: 서가지기는 단말기 관리자, 플레이어는 긴 이름 입력의 실제 효과를 조사하는 조사자다.
- 대상과 사건의 계기: 방문자 인사 단말기 프로그램(이름 입력 → "환영합니다" 응답). 긴 이름 입력 후 알아볼 수 없는 출력과 재시작처럼 보이는 동작이라는 제보.
- 길드를 찾은 이유: 서가지기는 그 글자들이 무엇인지, 왜 그런 일이 일어나는지 분석할 수 없었다.
- 이번에 공개할 정보: 컴파일된 프로그램 파일과 접속 주소, 터미널에 같은 라이브러리가 설치돼 있다는 사실. "복귀 주소", "라이브러리 유출", 함수 이름 같은 용어는 공개하지 않는다.
- 의뢰 목표와 완료 증거: 이름 입력만으로 단말기가 외부 명령을 실행하게 만들고 그 결과의 현재 flag를 제출. 새 연결에서 같은 두 단계 호출 연쇄만으로 성공해야 한다.
- 처음 전달할 사실: 호스트·포트, 프로그램 파일, 터미널에 설치된 동일 라이브러리, 한 줄 프로토콜(이름 → 응답, 연결 유지).
- 사건의 흐름: 평소 동작(이름 입력 → 인사말) → 제보(긴 이름 → 알아볼 수 없는 출력 → 재시작처럼 보임) → 서가지기가 원인을 모름 → 조사 권한(프로그램 파일·접속 주소) 전달 → 실제로 외부 명령 실행까지 이어지는지 조사.
- 조사 중 발견할 사실: 이름 입력이 복귀 위치까지 덮어쓸 수 있다는 것, 그 복귀 위치로 프로그램이 이미 쓰는 함수의 실제 주소를 출력시킬 수 있다는 것, 그 값과 로컬 라이브러리 파일로 다른 함수의 실제 주소를 계산할 수 있다는 것, 같은 방식으로 그 함수를 원하는 인자와 함께 부를 수 있다는 것.
- 풀이자에게 남긴 판단: 긴 이름의 실제 한계를 시험할지 여부, 오프셋·주소 계산, 어느 함수를 어떤 순서로 유출·호출할지, 라이브러리 파일을 어떻게 활용할지.
- 학습 목표와의 연결: 공유 라이브러리의 메모리 위치는 실행마다 달라지지만 라이브러리 파일 자체의 내부 구조(함수 사이의 거리)는 고정돼 있어, 함수 하나의 실제 주소만 유출돼도 다른 함수를 호출할 수 있다는 것을 직접 재현한다.

## 학습 목표와 대상

- 현재 계약의 category: "pwn"
- 학습 분야: System security(`learning-map.md`) 중 `pwn-mitigations`/`pwn-control-flow`의 결합 — "정보 유출이 특정 보호(주소 무작위화)를 약화시킨다"는 사례와 "구성된 호출 연쇄"의 결합이다.
- 세부 주제: 유출된 주소로 공유 라이브러리의 실제 위치를 계산하는 것(`library-base-recovery`), 그 위로 인자가 있는 호출을 구성하는 것(`argument-call-chains`의 적용).
- category 선택 근거: 메모리 쓰기 결함으로 주소 무작위화를 우회하고 공유 라이브러리의 임의 함수를 호출하는 문제로, `night-console`(정적 주소만 다룸)의 다음 단계다.
- 보안 학습 목표: 공유 라이브러리의 실제 위치가 매 실행 무작위화돼도, 그 라이브러리 안의 함수 하나의 실제 주소만 새어나가면 공격자가 같은 라이브러리의 다른 함수를 원하는 인자로 호출할 수 있다는 것을 설명할 수 있다.
- 확인할 보안 원리: 정보 유출에 의한 주소 무작위화 우회와 공유 라이브러리 함수 호출(`library-base-recovery`).
- 대상 풀이자: `night-console`에서 다진 호출 연쇄 구성(`argument-call-chains`)에 더해, 라이브러리 파일을 직접 읽어 오프셋을 확인하고 두 차례의 연쇄를 하나의 연결 안에서 순서대로 구성할 수 있는 풀이자. 디버거 사용은 요구하지 않는다.
- 시작 조건과 성공 증거: 프로그램 파일과 접속 주소가 주어지고, 터미널에는 대상과 같은 라이브러리가 이미 설치돼 있다. 이름 입력만으로 외부 명령이 실행되어 현재 flag가 나오면 성공이다.

## 의도된 풀이

| 단계 | 풀이자가 수행할 행동 | 발견·관찰할 내용 | 필요한 지식·도구 |
| --- | --- | --- | --- |
| 1 | 아주 긴 이름을 보내 본다 | 거부되지 않고 알아볼 수 없는 출력 뒤 다시 프롬프트로 돌아감. 반복하면 출력이 매번 달라짐 | 힌트 1 |
| 2 | `objdump`·`nm`·`readelf`로 `files/winlibc`의 오프셋과 `pop_rdi_ret`·`puts@plt`·`puts@got`·`main`의 주소를 확인한다 | 104바이트 채움 + 네 주소로 `puts`의 실제 주소를 유출시키고 `main`으로 되돌릴 수 있음 | 힌트 2, `argument-call-chains` |
| 3 | `nm -D /lib/x86_64-linux-gnu/libc.so.6`로 `puts`·`system`의 오프셋을 확인하고 라이브러리 시작 주소와 `system`의 실제 주소를 계산한다 | 두 번째 연쇄(104바이트 + `pop_rdi_ret` + `"echo $FLAG"` 문자열 주소 + 계산한 `system` 주소)로 외부 명령 실행 | 힌트 3, `library-base-recovery` |
| 4 | 같은 연결에서 두 연쇄를 순서대로 보낸다 | "pwnden{...}" | 해설 |

보안 학습 목표와의 연결: 2단계는 "복귀 위치 조작으로 이미 쓰이는 함수의 실제 주소를 새어나가게 할 수 있다"는 관찰을, 3단계는 "그 값과 고정된 라이브러리 구조로 다른 함수의 실제 주소를 계산해 호출할 수 있다"는 결론을 직접 재현하게 한다.

풀이자의 언어 지식: 코드 작성은 필요 없다. 두 번의 호출 연쇄를 순서대로 구성해 하나의 연결로 보내는 스크립트가 필요하다. 터미널에 설치된 라이브러리 파일을 직접 읽어 오프셋을 확인하는 것도 필요하다.

## 개념 관계

- 문제의 선수 개념: `argument-call-chains`(`night-console`이 가르침), `terminal-commands`.
- 문제의 학습 개념: `library-base-recovery`(`knowledge/library-base-recovery.md`) — 유출된 주소로 계산하는 라이브러리의 실제 위치.
- 개념 간 선수 관계: `library-base-recovery`는 `argument-call-chains`를 선수로 한다. 순환 없음.
- 관련 읽기: `night-console`(같은 pwn 계열의 이전 단계, 정적 주소만으로 인자 있는 호출을 구성한다).
- 공개 위치: 프로그램 파일, 접속 방법, 터미널에 같은 라이브러리가 있다는 사실은 본문에서 공개한다. 정확한 오프셋·주소·함수 이름·호출 순서는 힌트·해설에서만 명시한다.

## 난도 근거

- 선언한 값: 5 (1 입문, 2 초급, 3 중급, 4 고급, 5 심화)
- 선수 지식 부담: `argument-call-chains`(이전 문제에서 다짐) 위에 공유 라이브러리의 주소 무작위화와 오프셋 계산이라는 새 개념을 더한다.
- 발견 난도: 경계 시험(초과 입력 확인) → 오프셋·주소 계산(이름 버퍼·복귀 위치) → 유출 연쇄 구성(인자 있는 함수 호출의 재사용) → 유출값 해석과 라이브러리 오프셋 계산 → 두 번째 연쇄 구성과 같은 연결 안에서의 순서 관리, 총 다섯 단계로 `night-console`(단일 연쇄)보다 뚜렷이 더 많은 조합과 두 차례의 네트워크 왕복 관리가 필요하다.
- 구현 부담: 코드 작성 없이 두 개의 바이트 연쇄를 순서대로 구성하고 중간 응답을 파싱하는 스크립트가 필요하다.
- 풀이 의존성: 2단계(유출)의 결과가 3단계(주소 계산)의 입력이고, 3단계의 결과가 4단계(두 번째 연쇄)의 입력이라 전체가 순서대로 의존한다.
- 등급 판정: `night-console`(난도 4, 정적 주소만 사용하는 단일 연쇄)보다 한 단계(정보 유출 + 주소 무작위화 우회 + 두 차례의 연쇄) 더 복잡해 난도 5가 적절하다.

manifest의 difficulty를 바꾸면 이 기록도 함께 갱신하세요.

## 다른 풀이와 정답 노출

- 확인한 다른 풀이: 터미널의 `pwnden-cli:basic` 이미지가 대상과 같은 라이브러리 파일을 이미 포함한다는 것을 `sha256sum`으로 확인했다(별도로 라이브러리를 내려받거나 추측할 필요가 없다). `objdump`로 찾은 네 주소와 `nm -D`로 찾은 두 오프셋 외에 다른 값을 추측해 맞힐 수 있는 지름길은 없다.
- 의도치 않은 지름길 점검: 유출되는 raw 바이트는 정답 형식의 문자열이 아니며 매 실행 무작위이므로 과거 값을 재사용할 수 없다. `patched/test.py`로 패치된 서버에서는 같은 연쇄가 전혀 다른 효과(그냥 거부)를 낸다는 것도 확인했다.
- 본문 노출 점검: 본문은 프로그램 파일, 접속 방법, 같은 라이브러리가 설치돼 있다는 사실만 제공하고 어떤 함수를 유출·호출해야 하는지는 말하지 않는다. 파일을 그대로 실행하거나 짧은 이름만 보내서는 목표에 도달할 수 없다.
- 필요한 힌트: 1번은 긴 이름의 효과를 관찰하는 방향을, 2번은 유출 연쇄를 구성하는 도구와 방법을, 3번은 유출값으로 라이브러리 주소를 계산하는 방법을 각각 제공한다. 본문만으로는 두 차례의 연쇄가 필요하다는 단서가 부족해 3개를 유지한다.
- 해설: `solve/README.md`에 두 연쇄의 구성, 오프셋·주소 계산, 실제 성공, 패치 뒤 동작까지 기록했다.

## 검증과 리뷰

- 실행 범위: 실제 대상. 컴파일된 `files/winlibc`를 반복 실행해 유출값이 매번 달라짐과 계산한 `system` 주소로 외부 명령 실행이 매번 성공함을 확인했고(9회 반복, 실패 0회), 실제 TCP 서비스(`docker compose`)에 대해서도 같은 두 연쇄가 성공함을 확인했다. `tools/verify.py library-echo`로 취약한 서버에서 solve가 flag를 회수하고 패치 서버에서는 거부됨을 확인했다.
- 기술 검증: 2026-10-14, `objdump`·`nm`·`readelf`로 확인한 오프셋(이름 버퍼=rbp-0x60, 복귀 위치까지 104, `pop_rdi_ret`=0x401156, `main`=0x40115b, `puts@plt`=0x401030, `puts@got`=0x404000, 문자열=0x402004)과 터미널의 `/lib/x86_64-linux-gnu/libc.so.6`에서 확인한 오프셋(`puts`=0x802c0, `system`=0x53090)이 실제 공격 성공과 일치함을 확인했다. 컴파일에 쓰는 Debian 패키지 스냅샷을 이전 pwn 문제들과 같은 방식으로 고정해 주소가 빌드마다 바뀌지 않음을 확인했고, `sha256sum`으로 터미널의 라이브러리 파일이 대상 서버의 라이브러리 파일과 완전히 같음을 확인했다. 연결을 받는 Python 계층의 초기 구현이 `subprocess`의 기본 버퍼링된 `.read()`를 썼다가, 대상이 두 번째 입력을 기다리며 아직 살아 있을 때는 그 호출이 절대 반환되지 않는 교착을 발견해 `.read1()`로 고쳤다(이전 두 문제의 "먼저 보낸 뒤 기다리는" 클라이언트에서는 드러나지 않는 종류의 결함이었다). `tools/verify.py library-echo` 통과. `patched/test.py`가 평소 사용·경계값(63바이트)·이전 유출 연쇄를 모두 확인한다.
