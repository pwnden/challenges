## 조사 결과

이름을 받는 코드는 선언된 64바이트를 훨씬 넘는 길이를 받아들여, 저장된
복귀 위치까지 덮어쓸 수 있다. 복귀 위치를 레지스터 설정 조각과 `puts`
호출로 바꾸면, 이 프로그램이 이미 불러와 쓰는 `puts` 함수의 실제 메모리
주소를 그대로 출력시킬 수 있다. 그 값에서 터미널에 설치된 라이브러리
파일의 `puts` 오프셋을 빼면 라이브러리가 실제로 올라온 시작 주소를 알 수
있고, 같은 파일의 `system` 오프셋을 더하면 `system`의 실제 주소도 계산할
수 있다. 복귀 위치를 다시 한번 조작해 `system("echo $FLAG")`를 호출하면
서버 프로세스의 환경 변수에 있는 flag가 그대로 출력된다.

## 조사 과정

`files/winlibc`를 `file`로 확인하면 스트립되지 않은 x86-64 ELF 실행
파일이다. 실제 접속에서 긴 이름을 보내 보면 64바이트를 넘어도 거부되지
않고, 그 뒤로 알아볼 수 없는 몇 바이트가 출력된 뒤 "이름을 입력하세요:"로
돌아간다(다시 연결할 필요 없이 같은 연결이 유지된다). 이 바이트들은 접속할
때마다 달라지는데, 터미널에서 같은 프로그램을 반복 실행해 보면 역시 매번
달라진다 — 공유 라이브러리가 매 실행마다 다른 위치에 올라오기 때문이다.

`objdump -d -M intel files/winlibc`로 `main`을 읽으면 다음이 보인다.

```
48 8d 4d a0    lea rcx,[rbp-0x60]   # 이름 버퍼 시작
```

이름 버퍼(`rbp-0x60`)와 저장된 복귀 위치(`rbp+0x8`)의 오프셋 차이는
0x60 + 0x8 = 0x68 = 104바이트다. `nm files/winlibc`를 보면 레지스터를
설정하는 조각이 있다.

```
0000000000401156 T pop_rdi_ret
000000000040115b T main
```

`objdump -d`로 `puts@plt`를, `readelf -r`로 그 주소가 적힌 자리(`@got`)를
확인하면 각각 `0x401030`과 `0x404000`이다. 104바이트를 채운 뒤
`pop_rdi_ret`, `puts@got`의 주소, `puts@plt`의 주소, `main`의 주소를
8바이트씩 이어 붙여 보내면, 프로그램은 `puts(puts@got이 가리키는 값)`을
호출해 `puts`가 실제로 있는 메모리 주소를 그대로 출력한 뒤, 복귀 위치로
`main`을 돌려받아 프로그램 전체를 다시 시작한다. 같은 연결에서 다시
"이름을 입력하세요"가 온다.

터미널의 `/lib/x86_64-linux-gnu/libc.so.6`는 대상 서버가 쓰는 것과 같은
파일이다. `nm -D`로 읽으면 `puts`와 `system`이 그 파일 안에서 각각
`0x802c0`, `0x53090` 위치에 있다. 방금 얻은 `puts`의 실제 주소에서
`0x802c0`을 빼면 라이브러리가 올라온 시작 주소이고, 거기에 `0x53090`을
더하면 `system`의 실제 주소다. `strings -t x files/winlibc`로 찾은
`"echo $FLAG"` 문자열의 주소(`0x402004`, 프로그램 자신의 자료 영역에
있어 실행마다 바뀌지 않는다)를 인자로 넘겨 `system`을 호출하면, 서버
프로세스의 환경 변수에 담긴 flag가 그대로 출력된다. `system`은 내부에서
16바이트로 정렬된 스택을 요구하는 명령을 쓰므로, `pop_rdi_ret` 뒤에 단독
`ret` 하나를 더 끼워 그 정렬을 맞춰야 한다(끼우지 않으면 환경에 따라
호출이 조용히 실패할 수 있다).

## 의뢰 완료 확인

`app:9400`에 접속해 위 순서대로 두 번의 호출 연쇄를 같은 연결에서
차례로 보내면 `pwnden{...}` 줄로 현재 실행의 flag가 온다.
`solve/solve.py`가 터미널에 설치된 라이브러리 파일에서 오프셋을 직접 읽어
같은 과정을 자동으로 수행하고 그 값을 표준 출력에 그대로 출력한다.

## 드러난 보안 원리

공유 라이브러리는 매 실행마다 다른 위치에 올라오지만, 라이브러리 파일
자체는 고정돼 있어 그 안의 함수들 사이의 거리는 항상 같다. 그래서 프로그램
안의 어느 함수 하나의 실제 주소만 새어나가도, 같은 라이브러리의 다른 함수를
공격자가 원하는 인자와 함께 호출할 수 있다. 이번 문제에서는 메모리 쓰기
결함(이름 버퍼의 초과 쓰기)과 레지스터 설정 조각을 조합해 그 유출과 호출을
모두 이름 입력만으로 해냈다.

수정한 프로그램은 이름을 받는 코드 자체가 선언된 버퍼 크기(64바이트)만
받아들인다. `patched/test.py`가 평소 사용, 경계값(63바이트), 이전에
통하던 유출 연쇄를 모두 보내 봐도 응답이 "환영합니다"로만 남고 flag가
나오지 않음을 확인한다.
