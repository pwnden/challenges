# 문제 문장 검토 기준

문제 설명·의뢰인 대사·힌트·해설을 처음 읽는 사람이 상황과 조사할 일을
이해할 수 있는지 확인한다. 기술 설명은 대상의 실제 동작과 대조한다.
이 검토는 문서의 의미를 확인하는 필수 절차이며 별도 점수를 매기지 않는다.
학습 설계 점수와 실제 학습자 관찰은 [품질 평가](quality-review.md)에서 따로 관리한다.

## 확인 순서

1. 힌트·해설·구현을 열기 전에 브리핑과 제공된 자료만 읽는다.
   맨 위 의뢰 메시지가 있으면 먼저 그 블록만 읽고 의뢰인과 대상의 관계,
   문제가 된 자료·기능, 제보·증상, 확인할 일을 정리한다. 후속 본문을 읽은 뒤
   얻은 정보로 첫 메시지의 누락을 채워 통과시키지 않는다. 정확한 파일명·계정·
   주소는 별도 전달 정보에서 확인할 수 있다.
   의뢰인과 대상의 관계, 보호할 자료, 조사 이유, 제공한 접근 수단,
   플레이어가 확인할 일, 완료 증거를 자기 말로 정리한다.
   설명에 없는 내용은 추측으로 채우지 않고 빠진 정보로 기록한다.
2. 모든 문장을 문단 안에서 읽으며 아래 기준으로 확인한다.
   행동을 권하는 문장의 주어는 플레이어로 생략할 수 있다.
   매 문장에 의뢰인과 동기를 반복할 필요는 없다. 앞 문맥에서 대상을
   하나로 식별할 수 있으면 충분하다.
3. 구현과 검사 자료를 열고 기술적 주장을 하나씩 대조한다.
   본문이 제공한 정보와 해설을 본 뒤 알게 된 정보를 구분한다.
4. 수정한 문장은 앞뒤 문장과 함께 다시 읽는다. 기술적 의미나
   풀이 조건을 바꿨다면 관련 동작을 다시 확인한다.

## 판정 기준

| ID | 확인할 질문 | 통과 근거 | 수정해야 하는 경우 |
| --- | --- | --- | --- |
| T1 대상과 행동 | 누가 무엇을 하거나 할 수 있는가? | 행위자·대상·행동을 원문에서 식별할 수 있다. 행위자를 모르면 확인한 상태를 설명한다. | ‘기능이 정보를 제공한다’는 말만 있고 어떤 요청·자료인지 알 수 없다. 문장을 고치며 없던 행위자를 만든다. |
| T2 조사 이유 | 무엇이 걱정이며 플레이어가 어떤 질문에 답하는가? | 보호할 자료, 예상한 접근 범위, 확인할 일을 본문에서 연결할 수 있다. | ‘안전한 뜻인지 몰랐다’처럼 질문을 해석해야 한다. 근거 없이 의뢰인이 몰랐던 일이나 사고 경위를 덧붙인다. |
| T3 문장 연결 | 앞 문장과 다음 문장의 관계가 분명한가? | 지시어가 가리키는 대상이 하나이고 원인·추측·결과의 관계를 구분할 수 있다. | 안내 문구를 곧바로 인물의 믿음이나 사고 원인으로 취급한다. 서로 다른 자료·기능을 같은 말로 부른다. |
| T4 기술 표현 | 용어가 이번 대상의 구체적인 동작을 설명하는가? | 요청·응답, 파일 내용, 사용자 조작 등으로 의미를 풀 수 있고 이름을 실제 대상과 대응할 수 있다. | ‘정식 HTTP 기능’, ‘보호 경계’ 같은 표현만으로 무엇을 조사할지 짐작하게 한다. 기술 이름을 행위자나 권한 정책 대신 쓴다. |
| T5 사실과 근거 | 이 주장을 실제로 어디서 확인하는가? | 원문과 구현·배포 자료·대조 검사 또는 실행 기록을 연결하고, 근거가 입증하는 범위 안에서 말한다. | 403 하나로 로그인·담당자 계정·전체 접근 통제를 단정한다. 테스트 코드 존재를 실행 성공으로 쓴다. |
| T6 원칙과 동작 | 기대하는 보호와 실제 구현을 구분했는가? | ‘담당자만 읽어야 한다’는 운영 원칙, ‘요청이 403을 반환한다’는 동작, ‘다른 경로로 읽을 수 있을까’는 질문으로 구분한다. | 의뢰 설정을 구현 기능으로 단정한다. 제보·의심을 이미 확인한 사실처럼 설명한다. |
| T7 시작과 결론 | 선언한 선수 능력으로 시작하고 결과를 판단할 수 있는가? | 본문에 범위·자료·접근 방법·제출 대상이 있다. 힌트는 판단을 돕고 해설은 행동→관찰→결론을 연결한다. | 해설이나 코드를 읽어야 본문의 대상을 알 수 있다. 본문에서 핵심 발견이나 정답을 미리 알려 준다. |
| T8 한국어 표현 | 뜻을 유지한 채 자연스럽게 읽히는가? | 실제 행동을 익숙한 동사로 설명하고, 한 문장에 관계를 겹쳐 독자가 다시 해석하게 만들지 않는다. | 번역투·겹친 피동·추상 명사 때문에 뜻이 흐려진다. 능동형으로 고치다가 사실·의심·조건이 달라진다. |

T1–T8은 문장의 종류에 따라 적용한다. 예를 들어 기술적 주장이 없는 인물 소개에
실행 근거를 요구하지 않는다. 이해 검토에서 지적하는 누락은 선언한 선수 능력과
본문에 근거해야 한다. 모델이 헷갈렸다는 사실을 실제 초보자의 실패율로 표현하지 않는다.
한 문장에 여러 기준이 적용되면 하나의 발견에 해당 ID를 함께 적는다.
예를 들어 대상을 알 수 없는 기술 표현은 T4, 그 때문에 조사 행동도 알 수 없으면
T7을 함께 기록한다. 같은 결함을 여러 건으로 부풀리지 않는다.

구체적인 설명은 정답이나 발견할 명령을 미리 알려 준다는 뜻이 아니다.
기본 본문은 상황·목표·조사 범위·접근 정보·자료 위치·제출 대상을 제공한다.
읽은 뒤 풀이자가 직접 선택할 도구와 비교 기준을 적어 본다. 본문에 적힌 명령에서
파일명만 바꾸면 목표를 달성하거나, 핵심 필터와 판별 조건을 그대로 따라가면 되는
설명은 선택형 힌트나 해설로 옮긴다. 입문 문제도 이 구분을 적용한다.
개념 자료는 원리를 설명하고, 문제의 파일·주소·필드와 정답 절차를 연결하는 일은
풀이자에게 남긴다. 단순히 정답 문자열이 없다는 이유로 T7을 통과시키지 않는다.
HELP로 다음 명령을 찾는 것이 학습 목표라면 본문에는 연결 방법과 도움말을
확인할 시작 행동까지만 제공할 수 있다. 명령·필드명을 숨겼다는 이유만으로
수정 판정을 내리지 않는다. 선언한 선수 능력과 제공한 단서로 다음 관찰에
도달할 수 있는지를 확인하고, 기준을 충족하지 못하는 지점을 원문으로 설명한다.

## 주장과 증거 구분

기술적 주장에는 최소한 대상, 입력이나 조건, 관찰 결과, 적용 범위를 남긴다.
권한·보안·정답에 관한 주장은 해당 조건을 바꿨을 때의 대조 근거도 확인한다.

| 종류 | 사용할 근거 | 말할 수 있는 범위 |
| --- | --- | --- |
| 사건 설정·운영 원칙 | 브리핑 또는 작성자 설정 | 의뢰인의 역할과 바라는 보호 수준. 가상의 과거 사건을 실행으로 증명할 필요는 없다. |
| 구현 동작 | 대상 코드·배포 설정·제공한 파일 | 해당 조건에서 구현이 처리하는 동작. 이번 실행 성공을 뜻하지 않는다. |
| 관찰 결과 | 날짜·명령·조건·출력 또는 당시 실행 기록 | 관찰한 환경과 입력의 결과. 다른 계정·경로·환경으로 일반화하려면 추가 근거가 필요하다. |
| 의심·추론 | 단서와 판단 과정, 가능한 다른 설명 | 아직 확인하지 않은 질문 또는 근거가 지지하는 결론. 확정 사실과 구분한다. |

예를 들어 `diagnostic-port`의 대상 코드
`challenges/diagnostic-port/vulnerable/app.py`는 `/api/recovery` 요청에
`403`과 `staff_access_required`를 반환한다. 이 분기에는 로그인이나 담당자
계정을 확인하는 코드가 없다. 따라서 이 근거로 확인할 수 있는 것은 해당 요청의
거부 동작이다. 담당자 로그인 성공이나 다른 모든 접근 경로의 차단은 입증하지 않는다.
별도 TCP 기능의 접근 정책은 해당 처리 코드와 대조 검사를 추가로 확인한다.

하나의 문장에 구현과 현재 실행에 대한 주장이 함께 있으면 나눠 판정한다.
예를 들어 “허용 설정이면 코드를 반환한다”는 조건 분기로 확인할 수 있지만,
“지금 이 서버에서 코드를 읽을 수 있다”는 현재 설정과 실행 근거가 필요하다.
설정 자료를 아직 읽지 않았다면 두 번째 주장만 미확인으로 기록한다.
응답의 `staff_access_required` 문자열은 서버가 보내는 메시지이며,
그 이름 자체가 담당자 인증 기능의 존재를 입증하지 않는다.

브리핑은 운영 원칙을 다음처럼 표현할 수 있다.

> 보드 복구 코드는 운영 담당자만 읽을 수 있어야 한다.

요청 결과를 설명하는 문장은 다음처럼 구체적으로 쓴다.

> 복구 정보를 요청하면 웹 서버가 접근을 거부한다.

두 문장은 역할이 다르다. 브리핑에서는 필요한 상황과 질문까지만 제시하고,
구현 근거·명령·결과와 한계는 작성자 검토 기록이나 해설에 남긴다.

## 결과 기록과 완료 조건

판정은 `충족`, `수정 필요`, `미확인`, `해당 없음` 중 하나다.
`충족`에도 원문과 판단 이유를 남긴다. `해당 없음`은 적용하지 않는 이유를 적는다.
`미확인`은 자료 부족이며 좋은 문장이라는 뜻이 아니다.

문제별 검토는 `quality/text-reviews/<slug>/<run-id>.md`에 남긴다.
검토 날짜, 검토자, 소스 커밋, 검토한 문서·공통 지식 목록과 판본을 적고
각 T1–T8의 적용 범위·판정·근거를 표로 기록한다. 문장별 발견은 아래 형식으로 쓴다.
문제 디렉터리에 없는 공통 자료도 실제로 읽은 범위를 명시한다.
일부 파일로 기준 사용 시험을 하는 경우에는 읽은 파일과 제외한 범위를 적고
`제한된 기준 사용 시험`으로 표시한다. 전체 문장 검토 완료 기록과 구분한다.

| 위치·원문 발췌 | 기준 ID | 주장 종류·해석 | 근거 위치·발췌 또는 관찰 조건 | 판정·이유 | 수정안 또는 다음 확인 | 재확인 결과 |
| --- | --- | --- | --- | --- | --- | --- |
| 파일 경로와 제목/행, 정확한 원문 | T1–T8 중 해당 항목 | 원문이 실제로 말하는 내용 | 구현·자료·기록의 대응 부분. 비기술 문장은 문맥 | 구체적인 누락·불일치 또는 충족 이유 | 의미를 유지한 문장 또는 필요한 검사 | 수정한 판본과 결과 |

기술적 주장마다 대응 근거를 기록한다. 문제가 있는 문장은 하나씩 남긴다.
나머지 문장은 검토 범위별로 묶어 충족 근거를 기록할 수 있다.
소스를 바꾼 뒤 이전 기록을 새 판본의 검토 완료로 재사용하지 않는다.
기존 기록을 보존하고 변경한 문장과 연결된 문맥·주장을 다시 확인한다.

`수정 필요`나 적용 항목의 `미확인`이 남으면 문장 검토 완료로 표시하지 않는다.
문제의 총점이나 심사자의 다수 의견으로 확인한 결함을 상쇄하지 않는다.
필요한 단서를 숨기는 문제 설계와 본문 자체가 이해되지 않는 문제를 구분한다.
기술적으로 잘못된 문장, 시작·목표·제출 대상의 모호함은 관련 품질 평가 항목의
`reason`, `evidence`, `improvement`에도 반영한다. 점수는 기존 0–4 기준으로
판단하며 모든 문장 문제를 일괄 감점하거나 새 가중치를 만들지 않는다.

현재 `tools/quality.py`는 기존 평가 JSON의 형식·인용·해시를 검사한다.
이 문장 검토 표의 존재나 의미를 자동 검사하지 않는다. 검토자가 원문과 근거를
대조해야 한다. 기존 평가 점수는 이 절차를 수행했다는 증거로 취급하지 않는다.
