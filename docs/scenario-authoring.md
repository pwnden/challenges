# 시나리오 작성 틀

작성자는 시나리오를 만들고, 플레이어는 해킹 의뢰를 받아 해결한다.
의뢰의 배경과 제공된 자료가 조사할 이유를 만들고, 실제 관찰과 실험이 보안 개념을
드러내도록 설계한다. 시나리오는 기존 `challenge.toml` 계약으로 배포한다.

학습 목표·선수 지식·난도는 [작성 기준](authoring-standard.md)을 따르고,
시나리오별 설정과 근거는 생성된 `AUTHORING.md`에 기록한다.
아래 틀은 생성기의 기본 문서에도 적용된다.

## 문서의 역할

| 문서 | 플레이어가 읽는 내용 | 작성할 내용 |
| --- | --- | --- |
| `README.md` | 의뢰 브리핑 | 의뢰의 계기, 하나의 목표, 받은 자료·접근 정보, 시작에 필요한 배경 |
| `hints/1.md` 등 | 추가 정보 | 앞선 조사에서 확인할 관찰, 근거, 다음 행동을 점차 구체적으로 제공 |
| `solve/README.md` | 사건 보고서 | 실제 조사 과정, 재현 가능한 풀이, 완료 확인, 보안 원리와 개선 방법 |
| `AUTHORING.md` | 작성자 기록 | 시나리오 설정, 기술·학습 설계, 난도 근거, 검증과 학습 리뷰 |

웹사이트는 선언된 브리핑·힌트·해설을 기존 영역에 표시한다.
실행·도구·정답 제출은 플랫폼의 공통 기능을 사용한다.

## 어투

배경은 짧은 서술형으로 쓴다. “의뢰인이 게스트 계정 하나를 보내왔다”처럼 상황을
전달하고, 행동은 “비공개 메모를 찾아보자”처럼 플레이어에게 자연스럽게 제안한다.
의뢰인의 짧은 대사를 첫 문장으로 사용할 수 있다. 대사와 서술을 연결해 읽히게 쓴다.
각 인물의 대사는 설정된 성격·호칭·말투에 맞춰 다르게 작성한다.

계정·주소·파일·입력 형식은 따로 표시하고 정확한 값을 제공한다.
힌트는 “추가로 확인된 정보가 도착했다”는 느낌으로 실제 단서를 전달한다.
해설은 조사에서 무엇을 관찰했고 왜 그 결과가 나왔는지 설명한다.

문장마다 배경, 단서, 행동 또는 성공 조건을 전달한다. 대사와 사건 설정은 조사에
필요한 맥락만 담고, 문서 전체의 호칭과 어투를 일관되게 유지한다.

## 의뢰자와 의뢰 동기

길드에서 공개하는 인물 이름은 닉네임이다. 닉네임과 의뢰에 필요한 역할·대상 정보를
소개하고, 같은 인물이 다시 등장하면 그 목소리와 관계를 이어 간다.
인물의 공통 배경과 이번에 공개하는 정보를 작성 기록에서 구분한다.

확인한 증상, 직접 해결이 막힌 이유, 길드를 찾은 계기와 의뢰 목표를 연결한다.
소개·이전 의뢰·협업이 인물 관계와 이야기를 만든다. 전문 지식이 있는 의뢰자는
독립적인 재검증·추가 분석·협업이 필요한 상황에서 도움을 구한다.
브리핑에는 이번 조사에 필요한 동기를 짧게 담는다.

## 작성 순서

1. 학습 분야·세부 주제를 정하고 체험할 보안 원리와 관찰 행동을 하나 잡는다.
2. 실제 대상과 풀이 경로, 사용할 도구와 성공 증거를 먼저 설계한다.
3. 그 대상에 자연스럽게 연결되는 의뢰인의 닉네임·역할·말투, 길드를 찾은 계기와 사건을 정한다.
4. 브리핑에 공개할 사실과 조사 중 찾아낼 사실을 구분해 작성한다.
5. 필요한 선수 능력을 시작 전에 설명하거나 접근 가능한 학습 자료로 연결한다.
6. 추가 정보를 단계별로 작성하고, 사건 보고서에서 관찰과 원리를 회수한다.
7. 생성된 틀을 완성한 뒤 [검증](verification.md)과 학습 리뷰를 수행한다.

Intro 시나리오는 제공된 설명과 준비된 도구로 시작할 수 있게 설계한다.
Python은 작성·자동 검증에 활용하고, 플레이어의 요구 능력은 실제 풀이 행동을
기준으로 평가한다. 단서의 난도와 시나리오의 긴장감은 각각 설계한다.

## 의뢰 브리핑

아래 대괄호 부분을 완성하고, 해당 시나리오에 필요한 항목을 선택한다.
제목과 분야는 웹사이트의 헤더에서 표시하므로 본문은 의뢰로 바로 시작한다.

```markdown
> “[의뢰인이 전달한 짧은 메시지. 조사할 계기나 이상 징후를 담는다.]”

[누가 어떤 자료나 접근 권한을 보내왔는지, 대상이 어떤 역할을 하는지 설명한다.]

## 의뢰 목표

[찾을 정보 또는 입증할 행동을 하나 적는다. 완료를 확인할 결과까지 명확히 한다.]

## 전달받은 정보

- [계정, 접속 정보 또는 분석 자료의 역할과 정확한 값]
- [조사 시작점과 정상적으로 관찰할 수 있는 동작]

## 시작 전 알아둘 것

[첫 행동에 필요한 용어·도구 사용을 짧게 설명하거나 학습 자료로 연결한다.]

제출할 값은 `pwnden{...}` 형식이다.
```

### 브리핑 예시

> “우리 메모 사이트가 권한을 제대로 확인하는지 점검해 줘.”

의뢰인이 게스트 계정 하나를 보내왔다. 사이트에는 관리자의 복구 키가 담긴
비공개 메모도 보관돼 있다고 한다.

**의뢰 목표:** 게스트 계정으로 관리자의 메모를 읽고 복구 키를 확보하자.

**전달받은 계정:** `guest` / `guest`

제출할 복구 키는 `pwnden{...}` 형식이다.

이 예시는 문체의 기준이다. 실제 브리핑에는 해당 대상의 첫 행동에 필요한
배경과 실행 환경의 값 변경 등 필요한 조건을 함께 제공한다.

## 추가 정보

기본 세 단계는 다음 순서로 구체화한다. 단계 수는 시나리오의 조사 흐름에 맞춘다.

| 단계 | 역할 | 작성할 단서 |
| --- | --- | --- |
| 첫 정보 | 관찰할 방향 | 어느 동작이나 자료를 비교하면 되는지 알려 준다. |
| 다음 정보 | 관찰의 의미 | 차이가 나타나는 이유와 조사할 지점을 연결한다. |
| 마지막 정보 | 구체적인 실험 | 변경할 입력이나 재현할 행동, 확인할 결과를 안내한다. |

각 정보에는 실제 대상에서 확인할 수 있는 사실과 다음 행동을 담는다.
이야기 속 제보가 새로운 권한·파일·서비스를 제공한다면 실제 환경에서도 해당
자원을 제공한다. 기본 브리핑에는 출발 정보, 풀이 기법은 단계별 힌트에 배치한다.

## 사건 보고서

```markdown
## 조사 결과

[어떤 관찰을 통해 목표를 달성했는지 요약한다.]

## 조사 과정

[처음 받은 정보 → 실험 → 관찰 → 판단을 실제 수행 순서로 설명한다.]
[필요한 요청·명령·입력과 중간 결과를 제공해 같은 환경에서 재현할 수 있게 한다.]

## 의뢰 완료 확인

[정답을 확보하고 결과를 확인하는 방법을 설명한다.]
[고정 정답은 값을 제공하고, 실행마다 달라지는 정답은 현재 값을 얻는 과정을 적는다.]

## 드러난 보안 원리

[관찰이 보여 주는 보안 원리, 실패한 경계와 적절한 방어를 설명한다.]
[연결되는 선수 지식이나 다음 학습 자료가 있으면 링크한다.]
```

## 리뷰 기준

- 플레이어가 의뢰 배경과 목표를 첫 화면에서 이해할 수 있는가?
- 의뢰자의 공개 닉네임과 목소리가 일관되고, 길드에 조사를 맡길 이유가 자연스러운가?
- 자료·계정·도구·사전 설명만으로 첫 행동을 시작할 수 있는가?
- 의뢰 목표와 실제 풀이의 성공 조건이 일치하는가?
- 이야기의 모든 핵심 단서와 행동을 준비된 환경에서 확인할 수 있는가?
- 추가 정보가 실제 조사에서 막힌 지점을 풀어 주는가?
- 사건 보고서가 풀이의 이유와 보안 원리를 재현 가능한 과정으로 설명하는가?

설정과 말투의 검토는 학습·실행 리뷰와 함께 기록한다.
목표와 제공 정보는 한 번씩 명확히 제시하고, 세부 재현 과정은 보고서에 둔다.
