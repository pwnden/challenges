# 시나리오 작성 틀

작성자는 시나리오를 만들고, 플레이어는 해킹 의뢰를 받아 해결한다.
의뢰의 배경과 제공된 자료가 조사할 이유를 만들고, 실제 관찰과 실험이 보안 개념을
드러내도록 설계한다. 시나리오는 기존 `challenge.toml` 계약으로 배포한다.

학습 목표·선수 지식·난도는 [작성 기준](authoring-standard.md)을 따르고,
시나리오별 설정과 근거는 생성된 `AUTHORING.md`에 기록한다.
아래 틀은 생성기의 기본 문서에도 적용된다.

## 문서의 역할

| 문서 | 플레이어가 읽는 내용 | 작성할 내용 |
| --- | --- | --- |
| `README.md` | 의뢰 브리핑 | 의뢰의 계기, 하나의 목표, 받은 자료·접근 정보, 시작에 필요한 배경 |
| `hints/1.md` 등 | 추가 정보 | 앞선 조사에서 확인할 관찰, 근거, 다음 행동을 점차 구체적으로 제공 |
| `solve/README.md` | 사건 보고서 | 실제 조사 과정, 재현 가능한 풀이, 완료 확인, 보안 원리와 개선 방법 |
| `AUTHORING.md` | 작성자 기록 | 시나리오 설정, 기술·학습 설계, 난도 근거, 검증과 학습 리뷰 |

웹사이트는 선언된 브리핑·힌트·해설을 기존 영역에 표시한다.
실행·도구·정답 제출은 플랫폼의 공통 기능을 사용한다.

## 어투

배경은 읽기 쉬운 문장으로 충분히 설명한다. 인물이 무엇을 하던 중 어떤 일을 겪었는지
보여 주고, 행동은 “비공개 메모를 찾아보자”처럼 플레이어에게 자연스럽게 제안한다.
의뢰인의 짧은 대사를 첫 문장으로 사용할 수 있다. 대사와 서술을 연결해 읽히게 쓴다.
각 인물의 대사는 설정된 성격·호칭·말투에 맞춰 다르게 작성한다.
의뢰인의 대사는 아래 `message` 블록을 사용한다. `from`에는 공개 닉네임을 적는다.
플랫폼은 발신자와 대사를 본문과 구분된 메시지로 표시한다.

계정·주소·파일·입력 형식은 따로 표시하고 정확한 값을 제공한다.
힌트는 “추가로 확인된 정보가 도착했다”는 느낌으로 실제 단서를 전달한다.
해설은 조사에서 무엇을 관찰했고 왜 그 결과가 나왔는지 설명한다.

문장마다 배경, 단서, 행동 또는 성공 조건을 전달한다. 대사와 사건 설정은 조사에
필요한 맥락만 담고, 문서 전체의 호칭과 어투를 일관되게 유지한다.

인물이나 시스템의 행동은 “운영자가 파일을 올렸다”, “서버가 요청을 거부한다”처럼
주어와 동사로 직접 설명한다. 사건을 “파일이 공개됐다”, “요청이 거부되었다”처럼
피동형으로 옮기기보다 누가 무엇을 하는지 드러내는 자연스러운 한국어를 쓴다.
행위자를 모르면 확인한 상태나 가능한 행동을 설명한다. 예를 들어
“그 파일이 다른 사람도 받을 수 있는 곳에 공개됐다”는
“지금은 다른 사람도 그 파일을 내려받을 수 있다”로 쓴다.
문장을 바꾸려고 공개한 사람이나 공개 경위를 새로 만들지 않는다.
검토할 때는 의뢰인 대사·본문·힌트·해설에서 같은 기준을 확인한다.

인물이 궁금해하는 내용도 직접 쓴다. “그 말이 비밀값을 안전하게 보관한다는 뜻인지
알지 못했다” 대신 “다른 사람도 이 파일에서 복구 키를 읽을 수 있는지 확인해 달라고
맡겼다”처럼 대상과 질문을 밝힌다. “그 말”, “그것”, “그러한 방식”으로 앞 문장을 뭉뚱그리거나
“뜻인지 알지 못했다”로 설명을 돌아가지 않는다. 문법만 고치지 말고 사건의 흐름과
문장 사이의 연결까지 소리 내어 읽으며 확인한다.

기술 안내와 사건의 원인을 억지로 한 문장에 묶지 않는다. “안내에 Base64라고 적혀 있다”는
자료의 설명이고, “다른 사람이 파일에서 복구 키를 읽을 수 있을까”는 조사할 질문이다.
각 문장의 역할을 구분해 독자가 상황·걱정하는 이유·확인할 일을 순서대로 이해하게 쓴다.
“보호 경계”, “신뢰한 자료” 같은 추상 표현은 누가 어떤 자료를 읽는지, 무엇을 근거로
자료를 믿는지로 풀어 쓴다.

## 누구나 이해할 수 있는 설명

작성·수정 후 [문장 검토 기준](text-review.md)의 T1–T8을 적용한다.
상황과 질문은 브리핑만 읽고 확인하고, 기술적 주장은 실제 대상과 대조한다.
문법을 고친 것만으로 검토를 끝내지 않는다.

문제의 표시 제목은 한글로 짓고, 실제 상황이나 수행할 일을 알아볼 수 있게 적는다.
디렉터리·파일명·문제 식별자는 영문으로 관리한다. `challenge.toml`의 `title`이
웹사이트와 목록에서 보이는 제목이다.

계정은 계정, 문서는 문서, 접근 권한은 무엇을 읽거나 바꿀 수 있는지로 설명한다.
대상에서 실제로 하는 행동을 먼저 적고, 학습에 필요한 기술 이름을 이어서 소개한다.
예를 들어 “브라우저에 저장했다가 사이트에 다시 보내는 이름=값 데이터”를 설명한 뒤
‘쿠키’라고 부른다. 화면의 `Resource`는 “접근 규칙을 적용할 문서 이름”처럼
이번 문제에서 무엇을 가리키는지 알려 준다.

대사·브리핑·사이트 화면·힌트·해설은 같은 기능에 같은 이름을 사용한다.
이야기 속 물건과 기능은 실제 대상이나 전달 자료에서 확인할 수 있어야 한다.
비밀값이 있다면 무엇에 쓰는 값인지와 누가 볼 수 있어야 하는지를 설명한다.
처음 읽는 사람이 “누가 어떤 서비스를 쓰며, 무슨 일이 생겼고, 내가 무엇을 해야 하는가”를
자기 말로 설명할 수 있는지 확인한다.

## 의뢰자와 의뢰 동기

길드에서 공개하는 인물 이름은 닉네임이다. 닉네임과 의뢰에 필요한 역할·대상 정보를
소개하고, 같은 인물이 다시 등장하면 그 목소리와 관계를 이어 간다.
인물의 공통 배경과 이번에 공개하는 정보를 작성 기록에서 구분한다.

확인한 증상, 직접 해결이 막힌 이유, 길드를 찾은 계기와 의뢰 목표를 연결한다.
소개·이전 의뢰·협업이 인물 관계와 이야기를 만든다. 전문 지식이 있는 의뢰자는
독립적인 재검증·추가 분석·협업이 필요한 상황에서 도움을 구한다.
브리핑에는 의뢰인이 이 대상과 어떤 관계인지, 무엇 때문에 조사가 필요한지 담는다.

## 사건의 맥락

플레이어는 이 사이트와 인물을 처음 만난다. 작성자가 아는 배경을 본문에서부터
차근차근 제공한다. 다음 흐름이 이어지도록 문단을 나눈다.

1. **대상과 평소 동작:** 어떤 사이트·장치·자료이며 누가 무엇에 쓰는지 설명한다.
   ‘내보내기’처럼 처음 등장하는 기능은 이 대상에서 어떤 행동을 뜻하는지 풀어 쓴다.
2. **사건의 계기:** 원래 기대하던 동작과 어떤 제보·증상이 달라 조사를 맡겼는지 설명한다.
   확인된 사실과 의뢰인의 의심을 구분한다.
3. **의뢰인과 플레이어의 연결:** 의뢰인이 대상에 접근하거나 정보를 아는 이유,
   플레이어에게 맡기는 조사와 전달하는 자료·권한을 연결한다.
4. **조사의 출발점:** 파일별로 무엇을 기록했는지, 계정별로 누구의 자료를 볼 수 있어야
   하는지 설명한다. 서로 다른 자료가 있다면 함께 읽어야 하는 이유를 밝힌다.
5. **완료 결과:** 무엇을 찾아 어떤 값으로 제출하면 되는지 한 번 명확히 제시한다.

배경은 여러 문장과 문단으로 구성할 수 있다. 문장 수보다 인과관계와 정보의 역할을
기준으로 분량을 정한다. 닉네임·파일 이름·용어가 처음 등장할 때는 역할을 함께 소개한다.
상황을 이해하는 데 필요한 정보는 기본 브리핑에 담고, 실제로 찾아낼 주소·입력·사건의
결정적 기록은 조사와 단계별 힌트에서 발견하도록 구성한다.

스토리의 주장과 준비된 환경도 맞춘다. 파일 분석 의뢰라면 받은 기록으로 조사하고,
서비스 조사 의뢰라면 실제로 제공한 계정과 기능을 사용한다. 학습용 기록의 출처와
범위는 전달받은 자료에서 밝힌다. 작성자는 본문의 사건·자료·첫 행동을 구현이나
배포 파일의 근거와 대조한다.

## 작성 순서

1. 학습 분야·세부 주제를 정하고 체험할 보안 원리와 관찰 행동을 하나 잡는다.
2. 실제 대상과 풀이 경로, 사용할 도구와 성공 증거를 먼저 설계한다.
3. 그 대상에 자연스럽게 연결되는 의뢰인의 닉네임·역할·말투, 길드를 찾은 계기와 사건을 정한다.
4. 브리핑에 공개할 사실과 조사 중 찾아낼 사실을 구분해 작성한다.
5. 필요한 선수 능력을 시작 전에 설명하거나 접근 가능한 학습 자료로 연결한다.
6. 추가 정보를 단계별로 작성하고, 사건 보고서에서 관찰과 원리를 회수한다.
7. 생성된 틀을 완성한 뒤 [검증](verification.md)과 학습 리뷰를 수행한다.

Intro 시나리오는 제공된 설명과 준비된 도구로 시작할 수 있게 설계한다.
Python은 작성·자동 검증에 활용하고, 플레이어의 요구 능력은 실제 풀이 행동을
기준으로 평가한다. 단서의 난도와 시나리오의 긴장감은 각각 설계한다.

## 의뢰 브리핑

아래 대괄호 부분을 완성하고, 해당 시나리오에 필요한 항목을 선택한다.
제목과 분야는 웹사이트의 헤더에서 표시하므로 본문은 의뢰로 바로 시작한다.

```markdown
::message{from="[의뢰인의 공개 닉네임]"}
[의뢰인이 전달한 짧은 메시지. 조사할 계기나 이상 징후를 담는다.]
::

[의뢰인과 대상의 관계, 대상의 용도와 평소 동작을 설명한다.]

[어떤 제보나 사건으로 조사가 필요해졌는지, 무엇이 확인됐고 무엇을 의심하는지 설명한다.]

[플레이어에게 어떤 자료나 접근 권한을 맡기는지, 그것으로 무엇부터 조사할 수 있는지 연결한다.]

::objective

[찾을 정보 또는 입증할 행동을 하나 적는다. 완료를 확인할 결과까지 명확히 한다.]
::

::resources

- [계정, 접속 정보 또는 분석 자료의 역할과 정확한 값]
- [조사 시작점과 정상적으로 관찰할 수 있는 동작]
::

::knowledge

[첫 행동에 필요한 용어·도구 사용을 짧게 설명하거나 학습 자료로 연결한다.]
::

::submission
제출할 값은 `pwnden{...}` 형식이다.
::
```

각 블록은 역할을 표현하고, 제목·위계·표현은 플랫폼의 공통 UI가 제공한다.
`resources`의 기본 제목은 ‘전달받은 정보’다. 접속 계정이나 파일만 다룬다면
`::resources{title="접속 정보"}` 또는 `::resources{title="전달받은 자료"}`로 제목을 정한다.
블록 안에는 제목을 반복하지 않고 해당 내용을 작성한다. 이야기의 배경은 일반 문단으로 쓴다.

### 브리핑 예시

```markdown
::message{from="아직안잠"}
게스트가 운영 계정 자료를 받아 간 것 같아. 요청 기록은 있는데, 그때 실제로 뭘 받았는지까지 확인해 줄래?
::
```

사이트 기록을 정리하던 **아직안잠**에게서 의뢰가 도착했다. 이 사이트에서는 사용자가
‘내보내기’ 기능으로 자기 자료의 사본을 받아 간다. 자료에는 복구 키도 들어 있어,
다른 사람에게 전달되면 비밀값이 함께 노출된다.

게스트 계정 `guest`와 운영 계정 `ops`는 각자 소유한 자료만 받아 갈 수 있어야 한다.
그런데 아직안잠은 게스트가 운영 계정의 자료에 접근한 듯한 기록을 발견했다.
접근을 시도한 것인지, 자료까지 받은 것인지 확인하려고 당시 기록을 길드에 맡겼다.

전달된 `access.log`는 누가 어느 주소로 요청했는지, `audit.jsonl`은 누구의 자료를
무엇까지 전달했는지 기록한다. 두 파일은 같은 요청을 서로 다른 관점에서 남긴 자료다.

**의뢰 목표:** 게스트가 운영 계정의 자료를 실제로 받아 간 요청을 찾고,
그때 전달된 복구 키를 제출하자. 복구 키는 `pwnden{...}` 형식이다.

이 예시는 사건의 흐름을 설명하는 방식의 기준이다. 실제 브리핑에는 파일의 정확한
경로와 필드를 읽는 방법, 조사 시작에 필요한 배경도 함께 제공한다.

| 첫 정보 | 관찰할 방향 | 어느 동작이나 자료를 비교하면 되는지 알려 준다. |
| 다음 정보 | 관찰의 의미 | 차이가 나타나는 이유와 조사할 지점을 연결한다. |
| 마지막 정보 | 구체적인 실험 | 변경할 입력이나 재현할 행동, 확인할 결과를 안내한다. |

각 정보에는 실제 대상에서 확인할 수 있는 사실과 다음 행동을 담는다.
이야기 속 제보가 새로운 권한·파일·서비스를 제공한다면 실제 환경에서도 해당
자원을 제공한다. 기본 브리핑에는 출발 정보, 풀이 기법은 단계별 힌트에 배치한다.

## 사건 보고서

```markdown
## 조사 결과

[어떤 관찰을 통해 목표를 달성했는지 요약한다.]

## 조사 과정

[처음 받은 정보 → 실험 → 관찰 → 판단을 실제 수행 순서로 설명한다.]
[필요한 요청·명령·입력과 중간 결과를 제공해 같은 환경에서 재현할 수 있게 한다.]

## 의뢰 완료 확인

[정답을 확보하고 결과를 확인하는 방법을 설명한다.]
[고정 정답은 값을 제공하고, 실행마다 달라지는 정답은 현재 값을 얻는 과정을 적는다.]

## 드러난 보안 원리

[관찰이 보여 주는 보안 원리, 실패한 경계와 적절한 방어를 설명한다.]
[연결되는 선수 지식이나 다음 학습 자료가 있으면 링크한다.]
```

## 리뷰 기준

- 플레이어가 의뢰 배경과 목표를 첫 화면에서 이해할 수 있는가?
- 배경을 처음 읽은 사람이 대상의 평소 동작 → 이상 징후 → 맡은 조사 → 받은 자료의 관계를 자기 말로 설명할 수 있는가?
- 처음 등장한 인물·기능·계정·자료의 역할이 설명돼 있고, 의심과 확인된 사실이 구분되는가?
- 의뢰자의 공개 닉네임과 목소리가 일관되고, 길드에 조사를 맡길 이유가 자연스러운가?
- 자료·계정·도구·사전 설명만으로 첫 행동을 시작할 수 있는가?
- 의뢰 목표와 실제 풀이의 성공 조건이 일치하는가?
- 이야기의 모든 핵심 단서와 행동을 준비된 환경에서 확인할 수 있는가?
- 추가 정보가 실제 조사에서 막힌 지점을 풀어 주는가?
- 사건 보고서가 풀이의 이유와 보안 원리를 재현 가능한 과정으로 설명하는가?

설정과 말투의 검토는 학습·실행 리뷰와 함께 기록한다.
목표와 제공 정보는 한 번씩 명확히 제시하고, 세부 재현 과정은 보고서에 둔다.
