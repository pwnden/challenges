# 백업 중계기의 연결 상태 문장과 기술 대조

2026-10-14, Claude 작성자 검토. 소스는 작성 시점의 작업 트리 기준이다.
범위: `challenges/backup-relay/README.md`, 두 힌트, 해설, `vulnerable/app.py`,
`vulnerable/policy.py`, `patched/policy.py`, `patched/test.sh`.
실제 학습자의 독립 풀이 관찰은 포함하지 않는다.

| 범위·원문 | 기준 | 대응 근거 | 판정 |
| --- | --- | --- | --- |
| 첫 메시지의 AUTH 없이 READ만 보냈더니 응답이 왔다는 제보와 "직접 재현해 보지는 못했"다는 말 | T1, T2, T3, T6 | 자물쇠지기·중계기·제보·확인할 일을 첫 메시지만으로 식별한다. 제보를 이미 확인된 사실이 아니라 아직 재현되지 않은 의심으로 적었다. | 충족 |
| "AUTH 단계를 먼저 통과해야만 READ가 응답하게 만들었다고 설명한다" | T6 | 자물쇠지기가 기대하는 설계 의도를 설명으로 표기했고, 실제 구현이 그렇다고 단정하지 않는다. `vulnerable/app.py`의 `READ backup-current` 분기가 `authenticated`를 확인하지 않는 것과 대조된다. | 충족 |
| "STATUS 명령은 인증 전후로 다른 값을 돌려주는 것까지는 확인했다" | T4, T5 | `STATUS` 핸들러가 `authenticated`를 읽어 `role=guest`/`role=staff`를 반환하는 코드와 일치한다. | 충족 |
| 자료의 테스트 토큰 "AUTH 동작 확인용이며 현재 백업 열람 권한은 주지 않는다" | T5, T6 | `TOKEN`으로 `AUTH`는 성공하지만 `READ backup-current`의 성공 여부는 `READ_REQUIRES_AUTH`(취약: `False`)에만 좌우되어, 토큰 자체가 권한을 부여하지 않는다는 설명과 일치한다. | 충족 |
| "폐기된 백업 이름: backup-retired (제출 대상 아님)" | T5 | `READ backup-retired`는 고정 문자열을 반환해 매 실행 생성되는 flag와 형태로 구분된다. | 충족 |
| 힌트 1 "STATUS는 ... 실제로 기억한다는 뜻", "그 기억을 모든 명령이 똑같이 확인하는지는 아직 알 수 없다" | T3, T7 | 상태 추적 사실과 READ의 확인 여부를 분리해 다음 관찰(명령별 비교)로 이어지게 한다. 결론은 아직 말하지 않는다. | 충족 |
| 힌트 2 "AUTH를 한 번도 보내지 않은 상태에서 바로 READ backup-current만 보내 보자" | T7 | 구체적 시도를 안내하되 응답이 어떻게 나올지는 말하지 않는다. | 충족 |
| 해설 "READ를 처리하는 코드가 그 상태를 읽지 않아" | T4, T5 | `vulnerable/app.py`의 `READ backup-current` 분기가 `authenticated` 변수를 조건에 쓰지 않고 `READ_REQUIRES_AUTH`만 확인하는 코드와 일치한다. | 충족 |
| 해설의 패치 설명 "READ backup-current를 처리하기 전에 같은 authenticated 상태를 확인" | T5, T6 | `patched/policy.py`의 `READ_REQUIRES_AUTH = True`와 `patched/test.sh`의 AUTH 전/후 비교, 오답 토큰 거부, 정상 토큰 성공 검사가 이를 뒷받침한다. | 충족 |

기본 본문은 상황·목표·조사 범위·접근 정보·제출 대상을 제공한다. AUTH를 생략해도
되는지는 본문이 말하지 않고 풀이자가 직접 시도해야 한다. 숨은 주소나 명령어를
알아야 시작하는 단계는 없다. 난도 2의 부담이 적절한지와 재미는 학습자 관찰로
확인해야 한다.
